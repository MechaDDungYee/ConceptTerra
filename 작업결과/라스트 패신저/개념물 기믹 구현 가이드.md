# 개념물 기믹 구현 가이드

> 라스트 패신저 엔진 **버전 34**(절취선 사냥개 카드 배포 시점) 기준.
> 대상: 새 개념물 카드를 엔진에 실제로 넣는 개발자 또는 AI 코딩 도구.
> 이 문서의 코드 인용은 `public/rules.js`, `worker/game.js`, `public/game.js`, `public/grid.js`, `scripts/game.test.mjs`의 실제 함수명과 필드명을 그대로 쓴다. 이름이 나오면 그 이름으로 소스를 검색해 확인하라.

---

## 0. 이 문서를 읽는 방법

1. **§2를 먼저 읽는다.** 지금 엔진이 라운드를 어떤 순서로 처리하고, 카드 효과가 어느 시점에 누구를 대상으로 발동하는지를 알아야 §4의 구현 지시가 말이 된다.
2. **§3의 표로 현재 지원 범위를 확인한다.** "이미 되는 것"은 새 코드를 쓰지 말고 기존 효과 조합으로 카드를 정의한다. "안 되는 것"만 §4의 신규 어휘를 추가한다.
3. **§5의 통합표에 신규 어휘를 한 번에 등록한다.** 효과 하나를 추가할 때 `rules.js`·`worker/game.js`·`public/game.js` 세 곳에 동시에 등록하지 않으면, 커스텀 카드 저장·불러오기·편집기·미리보기가 조용히 깨진다(§5.8).
4. **§7의 테스트를 먼저 실패하게 만든 뒤 구현한다.** 기존 103개 테스트가 기준선이다.

표기 규칙:

- `worker/game.js:gameGrantStacks` = 파일:함수.
- "발동 시점 `hit`" = `rules.js`의 `timings` 키.
- 새로 추가하는 이름은 모두 **제안 이름**이며, 구현 시 §5 표와 일치시키면 된다.

## 1. 문서 목적과 관리 규칙

### 1.1 목적

이 문서는 「라스트 패신저」에 새 개념물 카드를 추가할 때, **현재 엔진이 그 기믹을 표현할 수 있는지**를 판정하고, 표현할 수 없을 때 **어떤 데이터·함수·테스트를 어떤 순서로 고쳐야 하는지**를 개발자와 AI 코딩 도구가 바로 실행할 수 있는 수준으로 적은 기술 명세서다. 세계관 설정 문서(예: `잡다한 것들/개념물 - 잔향의 유리 매미.md`)가 "무엇을 만들고 싶은가"를 정하고, 이 문서는 "그것이 코드에서 어떻게 굴러가야 하는가"를 정한다.

### 1.3 유지보수 규칙

새 개념물이 승인될 때마다 **이 문서를 같은 커밋에서 함께 갱신**한다.

1. §4.0 카드 명세 요약표에 새 개념물 행을 추가한다.
2. §3 표에 "그 기믹이 이미 되는지 / 안 되는지"를 판정해 적는다.
3. 안 되는 기믹마다 §4에 `4.x 기믹 — 이름` 절을 새로 만들고 (a)~(e) 다섯 항목을 모두 채운다.
4. §5 통합표에 새 어휘를 추가하고, §6.1 커밋 분할에 작업 항목을 추가한다.
5. §7에 회귀 테스트를 추가하고, 문서 첫머리의 "기준 버전 / 테스트 개수"를 배포 후 실제 값으로 바꾼다.
6. 문서를 고치는 커밋은 **1커밋 = 1변경** 원칙에 따라 코드 커밋과 분리한다.

### 2.2 전장과 좌표

```js
// public/grid.js
gridWidth = 8, gridHeight = 5, gridSize = 40
gridPoint(p) = {x: p % 8, y: Math.floor(p / 8)}
gridIndex(x,y) = y*8 + x        // 범위 밖이면 -1
gridDistance(a,b)               // 맨해튼 거리 (최대 7+4 = 11)
gridPaths(origin, limit, blocked)   // BFS, Map<도착칸, 경로배열>
gridDisplacement(source, target, pull)  // 한 칸 밀기/당기기 목적지
gridCardInRange(card, from, to) / gridInRange(range, from, to)  // '1~3', '0~11'
gridSplashTargets(card, actor, primary, units)
gridTileGroups(card, actor, tile, units, walls)
collapseTargets(card, actor, units)
```

- 벽: `worker/game.js`의 `gameWalls = [11, 27]`. 스폰: `gameSpawns = [16, 9, 25, 33]`(좌상·좌하·우상·우하).
- **전장 전체 사거리**는 새 개념이 아니라 `'0~11'` 문자열로 표현된다(최대 맨해튼 거리가 11). "사거리 전장 전체" 기믹은 이 값으로 이미 표현 가능하다.
- 좌표 → 화면 표기는 `public/game.js:battleGrid`의 `String.fromCharCode(65+x)+(y+1)` (예: `A1`, `H5`).

### 2.4 카드 데이터 구조

`worker/game.js:gameCard`가 검증·정규화하고, 내장 카드는 `gamePreset`/`gameEffect` 리터럴로 만든다. **내장 프리셋은 `gameCard` 검증을 거치지 않으므로 새 필드를 자유롭게 실을 수 있지만, 사용자가 복제·저장·가져오기 하면 `gameCard`가 다시 검증한다**(§5.8).

| 필드 | 예 | 비고 |
| --- | --- | --- |
| `id`, `name`, `notes`, `flavor`, `image` | `'conceptSuture'` | |
| `power` / `hitPowers` | `'3d+7'` / `['1d+4','1d+4']` | `parsePower` 형식. 타수 = `hitPowers.length` |
| `hitTargets` | `['all']`, `['primary','randomDistinct']` | 타격별 대상 모드 |
| `range`, `rangeShape`, `splash` | `'1~3'`, `{kind:'circle',radius:1}` | |
| `role`, `target`, `clash` | `'normal'`, `1`/`'self'`/`'area'`/`'splash'`/`'tile'` | |
| `cost` | `18` | 정신력 비용. 개념물은 `cardUsable`이 추가 검증 |
| `concept` | `true` | 개념물 표식 |
| `temporary` | `true` | 손패에 없어도 사용 가능한 환영 카드(붕괴/위기 카드) |
| `requiredState` | `'any'`/`'collapsed'`/`'awakened'` | |
| `optional` | `true` | 덱 편성 화면 노출 |
| `effects` | `[{when,kind,amount,to,tag,condition,limit,...}]` | 아래 |

효과 행(`gameEffect(when,kind,amount,to='target',tag='')`)이 실제로 해석하는 주요 필드:

| 필드 | 뜻 | 해석 위치 |
| --- | --- | --- |
| `when` | 발동 시점 | `gameTriggers` |
| `kind` | 효과 종류 | `gameApplyEffect` switch |
| `amount` / `amountExpr` | 고정값 / 계산식 | `gameFlowValue` |
| `to` | 수신자 | `gameEffectRecipients`, `to==='self'/'target'` 분기 |
| `tag` | 대상 중첩 이름 | `stack`/`consume`/`remove`/… |
| `condition` + `threshold` (+`conditionStackTag`) | 조건 | `gameEffectCondition` |
| `limit:{period:'turn'|'battle', count}` | 발동 횟수 제한 | `actor.effectUsage` |
| `amountMode:'fixed'|'percent'`, `ratioBasis`, `healthBasis` | 수치 해석 | `gameRatioAmount` |
| `scaleStack:'count'`, `scaleResource`, `scaleCost` | 배수 | `gameApplyEffect` |
| `hitIndex` | N타에서만 | `gameTriggers` 필터 |
| `stackCap`, `stackPower` | 부여 상한/위력 | `gameGrantStacks` |
| `consumeAmount:'all'`, `consumeScope:'total'`, `consumePriority` | 소모 방식 | `gameConsumeGroup` |

### 2.5 존과 카드 이동

```js
// worker/game.js
gameZoneEvents = {hand:'toHand', deck:'toDeck', grave:'toGrave', exile:'toExile'}
gamePlaceCards(b, unit, zone, ids, bottom=false, when=gameZoneEvents[zone])
gameDraw(unit, count, b)     // hand 12장 상한, 덱이 비면 묘지를 섞어 덱으로
gameFinishCard(b, ctx)       // 사용 카드의 최종 목적지 결정
```

- **덱의 맨 위 = 배열의 끝**이다. 뽑기는 `unit.deck.pop()`, 덱 위로 올리기는 `unit.deck.push(id)`, 덱 밑은 `unshift`.
- `gamePlaceCards`는 카드를 넣은 뒤 `gameCardZoneEvents`로 `toHand`/`toDeck`/`toGrave`/`toExile` + `handEntered` + `zoneEntered` 시점을 **전장의 모든 생존 유닛 카드에** 발동한다. 생성 카드가 손패에 들어오는 순간 다른 유닛의 반응 카드가 반응할 수 있다는 뜻이다.
- `gameFinishCard`의 목적지 결정:

```js
if(u.enemy||ctx.temporary)return;                       // 적 카드·환영 카드는 어디에도 남지 않음
if(ctx.destination==='hand'&&u.hand.length<12) ...       // return
else if(ctx.destination==='deckTop') ...                 // topdeck
else if(ctx.destination==='deckBottom') ...              // bottomdeck
else if(ctx.destination==='exile') ...                   // exile
else gamePlaceCards(b,u,'grave',[id]);                   // 기본
```

- 손패 상한 12, 드로우로 4장까지 보충(라운드 종료 시), 덱이 비면 묘지를 섞어 재활용한다. **묘지 순환을 타지 않는 카드는 `exile`(제외)로 보내야 한다.**

### 2.6 덱 편성 규칙

| 규칙 | 값 | 강제 위치 |
| --- | --- | --- |
| 덱 장수 | 정확히 10장 | `rules.js:deckSize`, `worker/game.js` `case 'deck'` (`보관함에서 카드 10장을 선택하세요.`) |
| 동일 카드 | 최대 3장 | `rules.js:deckCopyLimit` |
| 덱 미저장 시 | `gameStarterDeck` 10장으로 대체 | `gameDeck` |
| 사용 가능 카드 풀 | `gameCatalogue` + 보관함 | `gameBegin`의 `owned` |

`gameCatalogue = [...gameDefaults, gameCounterPreset, gameCopyPreset, ...gameResourcePresets, ...gameAwakeningPresets, ...gameConceptPresets]`이고, 유닛의 `library`는 이 카탈로그 **전체**를 담는다. 그래서 덱에 없는 카드라도 `giveCard`로 손패에 지급하면 정상적으로 사용할 수 있다(생성 카드 기믹의 전제).

### 2.7 라운드 처리 순서

`worker/game.js:gameResolve(b)`가 한 라운드를 끝까지 처리한다. 새 훅을 넣을 때 "몇 번째 단계인가"를 반드시 확인하라.

| # | 단계 | 관련 함수 / 시점 |
| --- | --- | --- |
| 1 | 라운드 초기화(`b.resolving`, `b.moved`, `b.proofs`, `b.poses`) | `gameResolve` 머리 |
| 2 | 조종 불가 유닛의 봇 계획 보충 | `gameBotTurn` |
| 3 | 계획 시점 효과 | `gamePlanningEffects` → `decide`, `confirm` |
| 4 | 각 유닛 이동 | `gameMove` (장애물 우회, `b.moved` 기록) |
| 5 | 카드 준비: 비용 지불, 대상 확정, `use` 시점, 패시브 `use` | `gamePrepareAction` |
| 6 | 첫 카드 웨이브 처리(합/반격/원호) | `gameResolveWave`, `gameClashEffects`, `gameStrike` |
| 7 | 2번째 이후 카드 웨이브 | `gameResolve` 루프 |
| 8 | 적 예고 공격 | `gameEnemyReady` → `gameCover` / `gameEnemyAction` → `gameUnopposedAttack` |
| 9 | 카드 마무리(목적지 결정, `end` 시점) | `gameFinishCard` |
| 10 | 턴 종료 효과(패시브·중첩) | `gameDeckEffects('turnEnd')` |
| 11 | 유닛별 턴 종료: 기본 중첩 피해 → 지연 타격 → 유예 피해 → 임시 보호막 → 지속 피해 → 재생 → 예약 보호막 | `gameBasicStackDamage`, `gameResolve` 중반 |
| 12 | 정신력 재생·연소, 심마 압박, 붕괴/각성 판정 | `gameMental`, `gameAwaken`, `gameConceptualize` |
| 13 | 손패 버리기, 이동력 재설정(`2 + nextMove`), 4장까지 드로우 | `gameDraw` |
| 14 | 상태 정리, `endDecay` 중첩 감소, `b.round++` | |
| 15 | 다음 라운드 준비(귀환 좌표, 적 예고, `turnStart`, 1라운드면 `battleStart`) | `gameNext` |

핵심 순서 두 가지:

- **비용은 5단계에서 지불되고, 피해는 6단계에서 발생한다.** 즉 빗나가도 비용은 이미 나갔다.
- **`hit` 시점은 기본 피해가 적용된 직후**다(`gameHitSequence`의 `strike` → `gameTriggerHit`). 그래서 "기본 공격 뒤 중첩 소모" 같은 문면은 `when:'hit'`으로 자연스럽게 만족된다.

### 2.8 발동 시점과 "누가 반응하는가"

`rules.js:timings`에 28개 시점이 있다. 같은 시점이라도 **반응 주체가 다르면 다른 함수**가 처리한다. 이 구분을 놓치면 "효과를 넣었는데 발동하지 않는다"가 된다.

| 반응 주체 | 처리 함수 | 발동하는 시점 |
| --- | --- | --- |
| 사용 중인 카드 자체의 효과 | `gameTriggers` | 카드에 적힌 `when` 전부 (`base`는 `use`로 승격) |
| 패시브 + **보유 중인 전용 중첩** | `gamePassives` | `battleStart`,`turnStart`,`turnEnd`(`gameDeckEffects` 경유), `decide`,`confirm`,`replace`,`use`,`clash`,`hit`,`damage`,`critical`,`noncritical`,`struck`,`hurt`,`attackEnd`,`unopposed`,`counter`,`end`, 그리고 카드 존 이동 5종 |
| 카드의 "피격 반응 창" | `gameCardReactions` | `struck`, `hurt` (지속 라운드 `reactionRounds` 보유 시) |
| 카드 존 이동 감시 | `gameCardZoneEvents` | `toHand`,`handEntered`,`zoneEntered`,`toDeck`,`toGrave`,`toExile` |
| 라운드 경계 | `gameDeckEffects` | `battleStart`,`turnStart`,`turnEnd` (덱에 든 카드 + 패시브 + 보유 중첩) |

즉 **전용 중첩은 "패시브처럼" 반응한다.** `conceptStacks`의 `effects`에 `{when:'turnStart'}`를 적으면 매 라운드 시작에, `{when:'struck'}`을 적으면 보유자가 맞을 때 발동한다. 다만 다음 두 구멍이 있다(§4.2).

- 적(`unit.enemy`)은 `gameEnemyAction`이 `gameTriggers`만 호출하고 **`gamePassives`를 호출하지 않는다** → 적이 보유한 중첩/패시브는 `use` 시점에 반응하지 못한다.
- **강제 이동 시점 자체가 없다.** `push`/`pull`/`swapPosition`/`retreat`는 위치만 바꾸고 어떤 시점도 발동하지 않는다.

### 2.9 중첩 처리

```js
gameGrantStacks(b, unit, effect, amount, trait, sourceRuns, dealer) → 실제 부여 개수
gameTakeStacks(unit, tag, count) → 소모한 총 위력
gameWriteStacks(unit, tag, runs) // count 0이면 stackTraits[tag] 삭제
gameSplitStacks(runs, count)     // 오래된 부여부터 소모
stackPotency(unit, tag)          // Σ(count × power)
```

- 상한은 **여러 출처의 최솟값**이다: `effect.stackCap`, `basicStacks[tag].cap`, `trait.cap`, `holdCount`(`gameGrantStacks` 첫 줄).
- 부여 시 `unit.stackTraits[tag] ??= trait`로 **최초 1회만** 정의를 등록한다. 정의를 나중에 바꾸려면 `unit.stackTraits[tag]`를 직접 교체해야 한다(§4.9).
- `count`가 0이 되면 `gameWriteStacks`가 `stackTraits[tag]`를 지운다 → `held` 보정이 즉시 사라진다(테스트 `removing a concept debuff immediately removes its held damage modifier and periodic damage`가 이 동작을 고정하고 있다).
- `held` 보정은 **`heldStackEffectKinds = ['critChance','critMultiplier','outgoingDamage','incomingDamage']`만** `gameHeldModifiers`에서 계산된다. 이 목록에 없는 종류를 `when:'held'`로 적으면 조용히 무시된다.
- 전투 종료 시 개념물 중첩은 `gameNext`가 정리한다: `if(trait.concept)gameWriteStacks(unit,name,[])`.

### 2.10 적 유닛의 특수성

- 적은 하나(`units.enemy`, 이름 `존속의 집행체`, hp 54, `boss=true`)이고, 매 라운드 `b.intent.card`(=`gameFoe`)로 공격한다.
- `gameMental`은 `u.enemy`면 0을 돌려준다 → 적은 정신력을 얻지도 잃지도 않는다.
- `cardUsable`이 `card.concept && unit.enemy`를 막는다 → 적은 개념물 카드를 쓸 수 없다.
- 적의 카드 사용 경로(`gameEnemyAction`)에는 `gamePassives`가 없다(§2.8).

### 2.11 수치 해석 규칙

| 표현 | 해석 |
| --- | --- |
| `amount` | 정수. `signed` 효과가 아니면 음수 불가 |
| `amountExpr` | `gameFlowValue`로 계산. `{type:'stat',stat:'selfHp'}` 같은 노드, `+ - × ÷ min max` 지원 |
| `amountMode:'percent'` | `gameRatioAmount`: 기본은 최대 체력 비율, `ratioBasis`로 기준 변경 |
| `scaleStack:'count'` | **`actor.stacks[card.name]`** 을 곱한다. 중첩 트레이트에서는 `card.name`이 곧 tag다 |
| `scaleResource` | 지불한 체력/정신력 배수 |
| `limit` | `period:'turn'`은 **`b.round`**, `'battle'`은 0. 즉 'turn'은 실제로 **라운드당**이다 |
| `hitIndex` | N타 전용. `wall`/`consume` 시점은 현재 타격과 일치해야 함 |

### 4.1 기믹 1 — 시동 카드가 파생 카드를 만들고, 중복을 막고, 소멸하고, 덱 위로 돌아온다

대상 카드: 외상 장부 `선지급`→`일괄 청구`, 잔향 `허물 흩뿌리기`→`일제 공명`, 수은 눈금 `끝점 점유`→`구석 붕괴`, 술래 `숫자 세기`→`찾았다`, 분해자 `점액 덮기`→`완전 소화`.

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **생성(손패 지급)은 된다.** `giveCard`(`givenCardId`)가 `gameTeachCard`로 상대 라이브러리에 카드를 심고 `gamePlaceCards(b,u,'hand',...)`로 손패에 넣는다. 생성 카드가 `gameCatalogue`에 있으면 `library`에 이미 있으므로 `gameSelect`의 "손패에 있는 카드를 선택하세요" 검증도 통과한다.
2. **중복 보유 판정이 없다.** "이미 손패나 덱에 남아 있으면 대신 다른 효과"를 표현할 조건이 `effectConditions`에 없다. `handLow`/`graveHigh`는 장수만 보므로 "그 카드가 있는지"를 알 수 없다.
3. **소멸이 반쪽이다.** `exile`(목적지)는 사용한 그 한 장을 제외 구역으로 보낼 뿐이고, ① 같은 id의 다른 사본, ② 묘지에 이미 쌓인 사본, ③ 제외 구역에서 되살리는 효과(`reclaim`, `recycleExile`)를 막지 못한다. "사용 후 덱과 묘지에서 제거"를 문자 그대로 만족하려면 새 처리가 필요하다.
4. **다른 카드를 덱 위로 올릴 수 없다.** `topdeck`/`bottomdeck`은 **지금 쓰는 카드 자신**의 목적지만 바꾼다. `recoverDeck`은 묘지의 최근 n장을 덱 위로 올릴 뿐 특정 카드를 지정할 수 없다.
5. **덱 편성 검증이 생성 카드를 막지 않는다.** `case 'deck'`은 "카탈로그에 있는 id 10장, 같은 카드 3장 이하"만 본다. 생성 카드에 표식이 없으면 플레이어가 10장 덱에 생성 카드를 3장까지 넣어 "시동 없이 생성" 루프를 만들 수 있다.
6. **`temporary:true`를 쓰면 안 된다.** `gameSelect`는 `card?.temporary&&cardUsable(u,card)`인 카드를 **손패에 없어도** 선택 가능하게 한다(붕괴/위기 카드용 장치). 생성 카드에 이 표식을 붙이면 손패에 없어도 매 턴 사용할 수 있게 되어 기믹이 붕괴한다.

#### (b) 필요한 데이터 스키마

카드 필드 추가:

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `generated` | `true` | 이 카드는 덱에 편성할 수 없고, 다른 카드의 효과로만 얻는다 |
| `exhaust` | `true` | 사용 후 제외 + 이번 전투에서 재획득 불가 |
| `exhaustUnlessKill` | `true` | (술래) 처치 시에는 예외 (§4.8) |

효과 종류 추가:

| kind | 필드 | 뜻 |
| --- | --- | --- |
| `postCard` | `postedCardId` | 지정 카드를 덱 맨 위로 올린다 |
| `purgeCard` | `purgedCardId` | 지정 카드의 모든 사본을 손패·덱·묘지에서 제거하고 재획득을 봉인 |

조건 추가:

| condition | 필드 | 뜻 |
| --- | --- | --- |
| `cardInZones` | `zoneCardId`, `zoneList:['hand','deck']` | 지정 카드가 해당 구역에 1장 이상 있는가 |

유닛 상태 추가:

| 필드 | 뜻 |
| --- | --- |
| `unit.purged: string[]` | 이번 전투에서 봉인된 카드 id. `reclaim`/`recycleExile`/`recover`가 참조 |

2. **같은 라운드에 시동 카드 2회 사용.** 행동량이 2 이상이면 같은 라운드에 두 번 쓸 수 있다. `cardInZones` 판정은 "지금 이 순간" 기준이므로 두 번째 사용 시점에는 첫 생성 카드가 손패에 있어 중복 분기로 간다. 의도된 동작이다.
3. **생성 카드가 묘지에 있을 때.** '일괄 청구'를 썼다가 소멸 처리 전에 묘지로 갔다면(예: `discardAllCost` 대가), 다음 시동 사용 시 중복으로 판정되어야 한다. `cardInZones`의 `zoneList`에 `'grave'`를 포함할지 결정해야 한다. **권장: `['hand','deck']`만** (문면이 "손패나 덱"이므로). 묘지 카드는 소멸 처리에서 어차피 제거된다.
4. **전투 종료 시 정리.** 유닛이 새로 만들어지므로 손패/덱/묘지의 생성 카드는 자동 소멸한다. 별도 코드 불필요.
5. **덱 위 복귀의 실제 효용.** 드로우는 라운드 종료 시 `4 - hand.length`장만 한다. 손패가 4장이면 덱 위 카드는 다음 라운드에도 뽑히지 않는다. 카드 문면의 "다음 턴에 다시 순환"을 실제로 보장하려면 `lateDraw`(+1)를 함께 주거나, 손패를 3장 이하로 쓰는 플레이를 전제로 해야 한다. **테스트에서 이 점을 명시적으로 확인**한다.
6. **`exhaust`와 `copySelf`.** 소멸 카드를 복제해 두 장 들고 있으면 두 장 모두 사용 가능하고, 첫 사용 시 `purgeCard`로 나머지 사본이 정리된다. 소멸 카드에 복제 효과를 붙이지 않는 것이 설계상 안전하다.

### 4.2 기믹 2 — 사건 기반 중첩 자동 누적과 라운드당 발동 제한

대상: 미수금(카드 사용), 잔향(피격), 좌표 낙인(강제 이동).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **"카드를 쓸 때마다"는 플레이어에게는 이미 된다.** `gamePrepareAction`이 `gamePassives(b,u,'use',...)`를 호출하고, `gamePassives`는 `gameHeldStackSources(actor)`를 소스에 포함한다. 즉 보유 중첩의 `{when:'use'}` 효과는 보유자가 카드를 쓸 때 발동한다(현재 '정각의 거주'가 이 경로를 쓴다).
2. **적에게는 안 된다.** 적의 카드 사용은 `gameEnemyAction`이 `gameTriggers`만 호출한다. 적이 '미수금'을 들고 있어도 이자가 쌓이지 않는다. 이 게임의 적은 매 라운드 카드를 쓰므로 치명적이다.
3. **"피격될 때마다"는 된다.** `gameStrike`가 `gamePassives(b,target,'struck',actor,event)`를 호출한다. 여기에 `{when:'struck',kind:'stack',to:'self'}`을 가진 중첩이 반응한다.
4. **"강제로 이동될 때마다"는 안 된다.** `push`/`pull`은 `gamePosition`으로 좌표만 바꾸고 아무 시점도 발동하지 않는다.
5. **"다음 판정 위력 −1"은 안 된다.** `gameHeldModifiers`가 계산하는 종류는 `heldStackEffectKinds`의 네 가지뿐이고, 판정 위력은 `gameActionPower`가 `unit.nextPower`만 보고 계산한다. `held`로 `weaken`을 적어도 무시된다.
6. **발동 횟수 제한은 이미 있다.** `effect.limit:{period:'turn',count:2}`가 `actor.effectUsage`로 **라운드당 2회**를 정확히 강제한다. 다만 `effectLimitPeriods`의 라벨이 '턴당'이라 의미가 어긋난다(코드는 `b.round`). 별도 `roundTriggerCounts` 맵을 새로 만들 필요는 없다 — 만들면 두 개의 카운터가 어긋나 디버깅만 어려워진다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 발동 시점 `forcedMove` | `timings`, `passiveTimings`에 등록. 강제 이동 1회당 1회 발동 |
| `heldStackEffectKinds` 확장 | `'weaken'`(다음 판정 위력) 추가. `gameActionPower`가 `gameHeldModifiers`를 읽도록 수정 |
| `effectLimitPeriods` | `round:'라운드당'` 추가하고 `limit.period`를 `'round'`로 쓰는 것을 표준으로 삼는다(`'turn'`은 하위 호환으로 유지) |
| 유닛 상태 | `unit.forcedMoveCount` 같은 신규 필드는 **불필요**(effectUsage 사용) |

미수금/잔향/좌표 낙인 정의 예:

```js
'미수금': {cap:5, description:'...', effects:[
  {when:'use', kind:'stack', to:'self', amount:1, tag:'미수금', limit:{period:'round',count:2}},
  {when:'turnEnd', kind:'fixedDamage', to:'self', amount:1, scaleStack:'count'}
]},
'잔향': {cap:3, description:'...', effects:[
  {when:'struck', kind:'stack', to:'self', amount:1, tag:'잔향', limit:{period:'round',count:2}},
  {when:'held', kind:'weaken', to:'self', amount:1}          // 중첩 수와 무관하게 −1
]},
'좌표 낙인': {cap:4, description:'...', effects:[
  {when:'forcedMove', kind:'stack', to:'self', amount:1, tag:'좌표 낙인', limit:{period:'round',count:2}},
  {when:'held', kind:'incomingDamage', to:'self', amount:8, amountMode:'percent',
   scaleStack:'count', condition:'attackerExclusiveEdge'}
]},
```

`잔향`의 −1은 카드 문면이 "다음 판정의 위력이 1 감소"로 중첩 수를 곱하지 않는다. **중첩당 −1로 의도한 것이라면 `scaleStack:'count'`를 붙인다**(문면 해석이 갈리는 지점이므로 구현 전에 확정한다).

#### (c) 파일별 구현

**`public/rules.js`**

1. `timings`에 `forcedMove:'강제 이동 시'`, `effectConditions`에 `attackerExclusiveEdge:'공격자가 단독 끝점'` 추가.
2. `passiveTimings`는 `timings`를 나열한 배열이 아니라 별도 목록이므로 `forcedMove`를 직접 추가한다.
3. `heldStackEffectKinds = ['critChance','critMultiplier','outgoingDamage','incomingDamage','weaken']`.
4. `effectLimitPeriods = {none:'제한 없음', turn:'턴당', round:'라운드당', battle:'전투당'}`.

**`worker/game.js`**

1. 적 카드 사용 훅:
   ```js
   function gameEnemyAction(b,actor,target){
     const ctx=gameContext(actor,b.intent.card,[target]);
     gameTriggerCardMark(b,actor,ctx.card);
     if(!gameAlive(actor))return ctx;
     gameTriggers(b,ctx,'use',target);
     gamePassives(b,actor,'use',target,ctx);   // 추가
     return ctx;
   }
   ```
   `gamePassives`는 `gameAlive(actor)`를 확인하고, `gameContext`는 적이면 `mod=0`이므로 판정 위력에 영향이 없다. `gameGrantStacks`는 적에게도 정상 동작한다.
2. 강제 이동 훅. `gameDamage`/`gamePosition`을 감싸는 헬퍼를 만든다.
   ```js
   // gameApplyEffect의 push/pull 케이스에서 이동 루프를 감싼다
   function gameForcedMove(b,u,actor,card,apply){
     const from=u.pos;
     apply();
     if(u.pos===from)return false;              // 실제로 움직이지 않았으면 발동하지 않는다
     const ctx=gameContext(actor,card,[u]);
     ctx.forcedFrom=from;ctx.forcedTo=u.pos;
     if(gameAlive(u))gamePassives(b,u,'forcedMove',actor,ctx);
     return true;
   }
   ```
   `push`/`pull` 케이스에서 칸별 이동을 마친 뒤 **한 번만** 호출한다(2칸 밀기 = +1). `swapPosition`, `retreat`, `evadeStep`도 같은 규칙으로 감싼다. "칸당 +1"로 설계를 바꾸려면 루프 안에서 호출한다.
3. 판정 위력의 held 보정:
   ```js
   // gameActionPower
   const held=gameHeldModifiers(b,unit,opponent||null);
   const modifier=ctx.mod+(unit.nextPower||0)+memory+awakening+(held.weaken||0);
   ```
   `gameHeldModifiers`는 `signed` 판정에 `ratioEffects.weaken[1] === -1`을 쓰므로 음수도 그대로 반영된다. `scaleStack:'count'`면 중첩 수가 곱해진다.
4. 라운드 카운터: `gameApplyEffect`의 `period` 계산을 확장한다.
   ```js
   const period=limit?(limit.period==='battle'?0:b.round):0;   // turn/round 모두 라운드 단위
   ```
   기존 코드는 `limit?.period==='turn'?b.round:0`이라 `'round'`를 추가하면 0이 되어 **전투당 1회로 조용히 바뀐다.** 반드시 위처럼 고친다.
5. `gameHeldModifiers`의 필터는 `heldStackEffectKinds.includes(effect.kind)`이므로 `weaken`이 자동으로 포함된다. `effect.condition`도 `gameEffectCondition`으로 평가되므로 `attackerExclusiveEdge`가 여기서 동작한다(§4.4).

**`public/game.js`**

1. `effectTiming`/`effectSentence`가 `forcedMove`, `weaken` held, `attackerExclusiveEdge` 문구를 표시하도록 `timings`/`effectConditions` 라벨을 그대로 쓰는지 확인(라벨 맵을 쓰므로 자동).
2. 전투 로그에 "강제 이동" 표시를 넣는다(`gameLog`는 워커에서 만들므로 `gamePassives` 발동 로그가 이미 남는다).

#### (d) 엣지 케이스

1. **피격 반응은 "공격"에만.** `gamePassives(b,target,'struck')`는 `gameStrike` 안에서만 호출된다. 지속 피해·고정 피해·함정 피해로는 잔향이 쌓이지 않는다. 문면이 "공격에 피격될 때"이므로 의도와 일치하지만, 테스트로 이 경계를 고정해 둔다.
2. **다중 타격 1회 = 피격 2회.** 2타 카드는 `gameStrike`가 두 번 호출되므로 잔향이 2회 시도된다. 라운드 2회 제한이 있으면 2타 한 번에 상한에 도달한다. 설계 확인 필요.
3. **적의 미수금은 라운드당 1회.** 적은 라운드에 카드를 1장 쓰므로 2회 상한에 닿지 않는다. 상한은 플레이어가 적에게 부여한 경우를 대비한 안전장치다.
4. **강제 이동이 막힌 경우.** 벽/경계로 한 칸도 못 움직이면 발동하지 않아야 한다(위 헬퍼의 `u.pos===from` 검사). 벽 충돌 `wall` 시점은 별개로 이미 발동한다.
5. **`swapPosition`은 두 유닛 모두 강제 이동**이다. 양쪽에 각각 발동시킬지, 시전자만 제외할지 결정한다(권장: 양쪽 모두, 단 시전자는 자기 카드로 자기를 옮긴 것이므로 제외).
6. **`edge` 판정이 필요한 held 조건**(`attackerExclusiveEdge`)은 `gameHeldModifiers(b,u,opponent)`가 `ctx.targets=[opponent]`로 호출하므로 `ctx.targets[0]`이 공격자다. 공격자가 없으면(지속 피해) 조건은 false.

```js
test('the enemy using its intent card grows its own 미수금', async()=>{ ... });
test('being struck adds 잔향 at most twice per round and lowers the next judgment by 1', async()=>{ ... });
```

### 4.3 기믹 3 — 인접 전이 · 광역 동시 타격 · 전장 전체 중첩 일괄 소모

대상: 잔향의 유리 매미(`허물 흩뿌리기`, `일제 공명`).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **전이를 `splash`로 흉내낼 수 없다.** `splash`는 카드의 **피해**를 부 대상에게도 넣는 장치다(`gameHitByTargetMode`의 `eligible`에 `card.splash&&unit!==primary`가 들어가고, `gameHitSequence`가 부 대상마다 실행된다). "중첩만 전이하고 피해는 주 대상만"은 표현 불가.
2. **`to:'secondary'`도 부적합.** `gameActionGroups`의 `secondary`는 `splash`에서만 채워지므로 결국 같은 문제다. `to`는 `targets.slice(1)`도 쓰지만 이는 다중 대상 카드(`target:2` 이상)의 두 번째 대상이다.
3. **합산 소모는 된다.** `consume` + `to:'allEnemies'` + `consumeScope:'total'`이면 `gameConsumeGroup`이 전장의 적 중 해당 중첩 보유자를 모아 총 위력을 `ctx.usedPotency`에 넣는다(테스트 `stack potency is separate from count and caps, and consumption uses the oldest grants first` 계열이 이 경로를 검증).
4. **그런데 피해는 한 명에게만 들어간다.** `gameTriggers`의 합산 분기는 `gameApplyEffect(...,units[0],applied,units)`를 **한 번** 호출한다. 그래서 `perStack`은 `units[0]` 한 명에게만 `총위력 × n`을 준다. "보유 적 전원에게 각각"은 불가.
5. **고정 피해 지정이 없다.** `perStack`은 `damage()` 헬퍼를 `fixed=false`로 호출한다. "고정 피해"를 요구하는 문면과 어긋난다.
6. **순서 보장이 없다.** "총합 계산 후 일괄 소모 및 피해"는 현재 구현이 이미 소모를 먼저 끝내고 `consume` 시점을 발동하므로 맞지만, 소모 도중 대상이 죽는 경우(반사 피해 등)를 다루는 규칙이 없다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 효과 `stackSpread` | `tag`, `spreadRange`(예 `'0~1'`), `to:'target'`(기준 대상) — 기준 대상의 인접 적에게만 중첩 부여 |
| 효과 `perStackGroup` | `amount`, `damageMode:'fixed'|'normal'` — 합산 소모에 참여한 모든 유닛에게 각각 피해 |
| `perStack` 확장(선택) | `damageMode:'fixed'` 지원 |
| 카드 필드(선택) | `damageMode` 없이도 `fixedDamage` 조합으로 대체 가능 |

`잔향` 중첩 정의:

```js
'잔향': {cap:3, description:'피격마다 1 증가(라운드 2회). 보유 중 다음 판정 위력 −1. 일제 공명으로 전부 소모되면 총 중첩당 고정 피해 4.', effects:[
  {when:'struck', kind:'stack', to:'self', amount:1, tag:'잔향', limit:{period:'round',count:2}},
  {when:'held', kind:'weaken', to:'self', amount:1}
]},
```

#### (c) 파일별 구현

**`public/rules.js`**

```js
newEffects.stackSpread=['인접 중첩 전이','hit','target','대상 인접 {n}칸 이내의 같은 편 적에게 지정 중첩을 {n} 부여'];
newEffects.perStackGroup=['소모 대상 전원 피해','consume','allEnemies','소모한 총 중첩 1당, 소모에 참여한 적 전원에게 각각 피해 {n}'];
```
`taggedEffects`에 `'stackSpread'`를 추가해 편집기에서 중첩 선택 UI가 뜨게 한다.

**`worker/game.js`**

1. `stackSpread`:
   ```js
   case 'stackSpread': {
     const trait=gameConceptTraits[tag]||actor.stackDefinitions?.[tag];
     const reach=effect.spreadRange||'0~1';
     const origin=u;                                   // u = 주 대상
     const targets=Object.values(b.units).filter(v=>
       gameAlive(v)&&v!==origin&&v!==actor&&v.enemy===origin.enemy&&
       gridInRange(reach,origin.pos,v.pos));
     for(const v of targets){
       const granted=gameGrantStacks(b,v,effect,n,trait,undefined,actor.id);
       if(granted)gameLog(b,actor.name+' · 잔향 전이 → '+v.name);
     }
     break;
   }
   ```
   주의: `u`는 `to:'target'`일 때 주 대상이다. `effect.to`를 `'target'`으로 두고 `when:'hit'`으로 발동시킨다. 전이는 **적 편만** 대상이다(`v.enemy===origin.enemy`, `origin`은 적이므로 적끼리).
2. `perStackGroup`. 합산 소모 분기에서 그룹을 ctx에 남긴다.
   ```js
   // gameTriggers, consumeScope==='total' 분기
   ctx.effectRecipients.set(effect,{units,applied});
   ctx.consumeTargets=units;                     // 추가
   ```
   그리고 switch:
   ```js
   case 'perStackGroup': {
     const potency=ctx.usedPotency||0;
     if(!potency)break;
     const group=(ctx.consumeTargets||[]).filter(gameAlive);
     const amount=potency*n;
     for(const victim of group)gameDamage(b,victim,amount,actor,false,false,effect.damageMode==='fixed',{kind:'stack'});
     gameLog(b,actor.name+' · 소모한 중첩 '+potency+' → '+group.length+'명에게 각각 '+amount);
     break;
   }
   ```
   **중요:** `gameDamage`는 `fixedDamage=true`면 `u.reduce`(피해 경감)를 건너뛰고 보호막은 적용한다. 문면의 "고정 피해"와 정확히 일치한다.
3. 사망 처리 순서. 위 루프는 대상 배열을 먼저 확정한 뒤 순차 적용하므로, 한 명이 죽어도 나머지는 계속 맞는다. "동시"를 더 엄격히 지키려면 총 피해량을 먼저 계산해 배열에 담고 일괄 적용한다(권장: 그대로 순차 적용하되, `gameAlive` 필터를 루프 밖에서 한 번만).
4. `perStack`에 `damageMode` 지원을 추가할 경우:
   ```js
   case 'perStack': if(ctx.usedPotency)damage(ctx.usedPotency*n,false,effect.damageMode==='fixed');break;
   ```

**`public/game.js`**

1. `renderCardFace`/`effectSentence`가 새 효과의 문장을 표시하도록 `newEffects` 라벨을 쓴다(자동).
2. 전투 로그에서 "N명에게 각각" 문구가 읽히는지 확인.

#### (d) 엣지 케이스

1. **전이 기준이 "주 대상"인지 "시전자"인지.** 문면은 "대상 인접 1칸 이내의 다른 적". 시전자 기준으로 읽으면 원거리 카드에서 의미가 달라진다. 기준 대상을 `effect.spreadFrom:'target'|'actor'`로 명시한다(권장 기본값 `'target'`).
2. **전이된 중첩도 상한을 지킨다.** `gameGrantStacks`의 `room` 계산으로 자동 처리(잔향 상한 3).
3. **전이 대상이 자기 자신(주 대상)이면 제외**해야 한다(`v!==origin`).
4. **일제 공명이 빗나간 경우.** `hit` 시점이 발동하지 않으면 소모도 피해도 없다. 다만 비용은 이미 지불됐다(§2.7).
5. **일제 공명의 주 대상이 죽은 경우.** 부 대상(전장 전체)은 주 대상과 무관하게 `consumeGroup`으로 수집되므로, 주 대상이 쓰러져도 다른 적의 잔향은 소모·피해 대상이 된다. 이를 원하지 않으면 `gameTriggers`의 `!gameAlive` 가드 위치를 확인한다.
6. **소모 우선순위.** `consumePriority` 기본값은 `lowestHp`(체력 가장 적은 적). 상한까지 일부만 소모하는 경우(`consumeAmount:'fixed'`) 우선순위가 결과를 바꾼다. 일제 공명은 `'all'`이므로 무관.

### 4.4 기믹 4 — 2D 그리드 상대 위치 판정 `[단독 끝점]`과 조건부 분기

대상: 수은 눈금의 경사 도마뱀(`끝점 점유`, `구석 붕괴`).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **위치 조건이 전혀 없다.** `effectConditions`의 위치 관련 항목은 `near`/`far`(거리)뿐이다. 끝줄·모서리·단독 점유를 표현할 수 없다.
2. **판정 함수가 없다.** `grid.js`에는 거리·경로·범위만 있고 "누가 어느 끝에 혼자인가"를 계산하는 함수가 없다.
3. **정반대편 대상을 고를 수 없다.** `effectRecipients`에 위치 기반 수신자가 없다.
4. **사용 시점 스냅샷이 없다.** `ctx`는 `gamePrepareAction`에서 만들어지지만 위치 판정 결과를 담지 않는다. 라운드 중 밀림으로 위치가 바뀌면 같은 카드의 여러 효과가 서로 다른 판정을 보게 된다.
5. **밀기/끌기 선택 입력이 없다.** `push`와 `pull`은 별개 효과다. "밀거나 끌어당긴다(선택)"은 계획 입력이 필요하다(`gameSelect`는 `pos`/`targets`/`clash`/`discard`/`copyId`/`vow`만 받는다).
6. **아군 지정이 없다.** `gameAllowedTargets`는 `v.enemy!==u.enemy`만 돌려준다.

#### (b) 필요한 데이터 스키마

`public/grid.js`에 순수 함수:

```js
export function gridExclusiveEdges(unit, units){
  const {x,y}=gridPoint(unit.pos);
  const others=units.filter(v=>v&&v!==unit&&v.hp>0);
  const aloneIn=(test)=>!others.some(v=>test(gridPoint(v.pos)));
  const top=y===0&&aloneIn(p=>p.y===0);
  const bottom=y===gridHeight-1&&aloneIn(p=>p.y===gridHeight-1);
  const left=x===0&&aloneIn(p=>p.x===0);
  const right=x===gridWidth-1&&aloneIn(p=>p.x===gridWidth-1);
  const dirs=[top&&'top',bottom&&'bottom',left&&'left',right&&'right'].filter(Boolean);
  return {top,bottom,left,right,count:dirs.length,dirs};
}
```

규칙:
- 판정 대상은 **살아 있는 모든 유닛**(아군·적·봇 포함). 쓰러진 유닛은 세지 않는다.
- 같은 끝줄에 다른 유닛이 하나라도 있으면 그 방향은 단독이 아니다.
- 모서리(x==0&&y==0 등)면 두 방향이 동시에 true → `count===2`.
- 벽(`gameWalls`)은 유닛이 아니므로 판정에 영향이 없다.

효과 조건 추가:

| condition | 뜻 |
| --- | --- |
| `exclusiveEdge` | `ctx.edges.count >= threshold` (1이면 아무 방향, 2면 모서리) |
| `edgeTop` / `edgeBottom` / `edgeLeft` / `edgeRight` | 개별 방향(flagConditions에 넣어 임계값 입력 없이 체크박스로) |
| `edgeVertical` / `edgeHorizontal` | 상·하 / 좌·우 묶음(모서리 2중 발동을 두 효과로 나눌 때) |

수신자 추가:

| to | 뜻 |
| --- | --- |
| `oppositeEdgeEnemies` | 시전자의 단독 방향의 **반대편 끝줄**에 있는 적 전원. 모서리면 두 방향의 합집합 |
| `edgeEnemies` | (선택) 같은 끝줄의 적 |

flowStat 추가: `edges`(= `ctx.edges.count`).

카드 필드(선택): `targetSide:'enemy'|'ally'|'any'`.

계획 입력 추가: `displace:'push'|'pull'`.

**`public/rules.js`**

1. `effectConditions`에 위 6개 항목, `flagConditions`에 `edgeTop`…`edgeHorizontal`을 넣는다.

**`worker/game.js`**

1. 컨텍스트 스냅샷. `gamePrepareAction`에서 `ctx` 생성 직후:
   ```js

   ```
   `gameContext`를 고치지 않고 `gamePrepareAction`에서 넣는 이유: 계획 시점(`gamePlanningEffects`)에는 이동 전 위치이므로 판정 시점이 다르다. "사용 시점"은 이동 후·효과 발동 전인 5단계다.

5. 밀기/끌기 선택:

6. 아군 지정(선택):

   ```js
   function gameAllowedTargets(b,u,card){
     if(card.role==='counter')return [u];
     if(card.target==='self')return gameAlive(u)&&gameReach(card,u,u)?[u]:[];
     const side=card.targetSide||'enemy';
   ```

#### (d) 엣지 케이스

1. **동률 판정.** 같은 줄에 적과 아군이 모두 있으면 단독이 아니다. "다른 유닛"을 진영 구분 없이 세는 것이 카드 문면("전장의 모든 유닛(아군·적 포함)")과 일치한다.
2. **모서리 2방향.** `count===2`. 시동 카드의 회복은 `amountExpr`로 `edges × 4`(보호막), `edges × 3`(정신력)을 주면 모서리에서 자동으로 2배가 된다. 별도 분기 코드가 필요 없다.
3. **모서리에서 상·하/좌·우 두 효과 동시 발동.** `condition:'edgeVertical'`과 `'edgeHorizontal'`을 단 효과 두 개를 나란히 두면 모서리에서 둘 다 발동한다. 효과 배열 순서가 곧 실행 순서다.
4. **판정 시점.** 이동 후 스냅샷이므로, 같은 라운드에 적이 먼저 움직여 끝줄이 바뀌어도 카드 효과는 사용 시점 기준으로 일관된다. 반대로 "피해 시점에 재판정"을 원하면 `ctx.edges`를 지우고 조건에서 라이브 계산한다(권장하지 않음: 같은 카드 안에서 효과마다 결과가 달라진다).
5. **반대편 끝에 적이 없는 경우.** `oppositeEdgeEnemies`가 빈 배열이면 그 효과만 발동하지 않는다(`gameTriggers`의 수신자 루프가 빈 배열을 순회).
6. **벽 위의 유닛.** `gamePosition`이 벽을 막으므로 유닛이 벽 칸에 있을 수 없다. 끝줄 판정에 벽을 고려할 필요가 없다.
7. **보호막 4×방향 수의 상한.** `shield`는 `Math.min(999, u.shield+n)`로 상한이 있다.
8. **`[단독 끝점]`이 아닐 때 시동 카드의 생성.** 문면은 "단독 끝점이라면 … 생성"이므로, 단독이 아니면 생성 카드도 만들지 않는다. 조건을 생성 효과에 직접 건다(`condition:'exclusiveEdge'`, `threshold:1`).
9. **정신력 회복의 상한.** `gameMental`이 100에서 자른다. 100일 때 회복 효과는 로그 없이 0이 된다(설계상 정상).

### 4.5 기믹 5 — 중첩 소모 시 자원 환급과 조건부 방어막·위력 변동

대상: 외상 장부의 정신력 회복, 수은 눈금의 끝점 수 비례 보호막·정신력, 술래의 각성 정신력 회복.

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **체력·보호막 버전만 있다.** `consumeHeal`(= `소모한 총 위력 1당 체력 n`)과 `shieldPerStack`은 있지만 **정신력 버전이 없다**. `gameApplyConversion`이 `output==='mind'`를 지원하므로 배관은 이미 있다.
2. **끝점 수 비례는 통계가 없다.** `edges` flowStat이 없으면 `amountExpr`로 `4 × 방향수`를 쓸 수 없다(§4.4에서 함께 추가).
3. **적용 시점 규칙이 문서에 없다.** 비용은 5단계(계획 실행), 환급은 6단계(적중)에 일어난다. "계획 시점이 아니라 실제 적중 시점"을 보장하는 것은 이 순서 자체다. 다만 **빗나가면 비용만 나가고 환급이 없다**는 점을 카드 문구와 테스트로 명시해야 한다.
4. **상한 초과 방지**는 `gameMental`의 `bounded(old+delta,0,100)`로 이미 보장된다. 별도 clamp 코드를 쓰지 말고 `gameMental`의 반환값(실제 증감)을 로그에 쓴다.
5. **`usedPotency`의 수명.** `consume` 케이스가 `ctx.usedPotency`를 설정하고 `gameTriggers(b,ctx,'consume',...)`를 호출한 뒤 **되돌린다**. 따라서 환급 효과의 `when`은 반드시 `'consume'`이어야 한다. `'hit'`이나 `'end'`에 적으면 `usedPotency`가 없어 아무 일도 일어나지 않는다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 효과 `mindPerStack` | `consume` 시점, 소모한 총 위력 1당 정신력 n 회복 |
| flowStat `edges` | §4.4와 동일 |
| (기존) `shieldPerStack`, `consumeHeal` | 그대로 사용 |

카드 효과 예(외상 장부 `일괄 청구`):

```js
{...gameEffect('hit','consume',1,'target','미수금'),consumeAmount:'all'},
gameEffect('consume','perStack',4),
gameEffect('consume','mindPerStack',2)
```

수은 눈금 `끝점 점유`의 회복:

```js
{when:'hit',kind:'shield',to:'self',condition:'exclusiveEdge',threshold:1,
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'edges'},{type:'number',value:4}]}},
{when:'hit',kind:'mind',to:'self',condition:'exclusiveEdge',threshold:1,
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'edges'},{type:'number',value:3}]}}
```

#### (c) 파일별 구현

**`public/rules.js`**

```js

```
`effects`에 자동 반영되고, `passiveEffectKinds`에도 `'mindPerStack'`을 추가한다(패시브에서도 쓰게 할 경우).

**`worker/game.js`**

```js

  if(!potency||u.enemy)break;
  const restored=gameMental(b,u,potency*n);
  if(restored>0)gameLog(b,u.name+' · 미수금 정산 · 정신력 +'+restored);

```

주의 사항:

- `gameMental`은 `u.enemy||u.collapsed`면 0을 돌려준다. 적이 자기 중첩을 소모해 정신력을 얻는 설계라면 `gameMental`을 우회하는 별도 처리가 필요하다(현재 게임에서 적 정신력은 쓰이지 않으므로 무시해도 된다).
- `mindGuard`/`mindRecoveryCut`은 `unmodified=false` 경로에서 적용된다. 회복 감소 저주를 받은 상태라면 환급도 깎인다. 의도인지 확인한다(권장: 카드 문면이 "회복"이므로 그대로 적용).

**`public/game.js`**

`effectSentence`가 `소모한 중첩 1당 정신력 2 회복`을 표시하도록 라벨을 추가한다.

#### (d) 엣지 케이스

1. **소모 0.** `consume` 케이스는 `if(used)`일 때만 `consume` 시점을 발동한다. 중첩이 없으면 환급도 피해도 없다(기본 공격만).
2. **정신력 100.** 환급이 0이 되고 로그도 남지 않는다. `restored>0` 조건으로 조용히 처리.
3. **붕괴 직전 상태.** `gameMental`은 `u.collapsed`면 0. 붕괴 직전(`zero==='crisis'`)은 회복 가능하며, 회복하면 `gameMental` 내부에서 위기 해제 로그가 남는다. 환급 카드가 붕괴 탈출 수단이 되는 것은 설계상 허용할지 결정한다.
4. **환급이 붕괴/폭주를 유발하는가.** 회복은 위기를 유발하지 않는다. 반대로 `mindCost`(비용)가 0으로 떨어뜨리면 폭주 위기가 된다.
5. **다중 대상 소모.** `consumeScope:'total'`이면 `usedPotency`가 전장 합산이다. 환급도 총합 기준이 된다(의도된 동작, 테스트로 고정).

### 4.6 기믹 6 — `[술래 각성]` 상태 감지 (아군 사망 훅과 1인 단독 판정)

대상: 눈 가린 마지막 술래(`숫자 세기`, `찾았다`).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **아군이 쓰러지는 순간을 알 수 없다.** `gameDamage`는 `hp`를 깎고 `u.hp===0`이면 로그만 남긴다. "아군이 죽었다"를 관찰하는 시점이 없다.
2. **1인 단독 판정이 없다.** `gameNext`는 `party`(살아 있는 아군 배열)를 만들지만 `party.length===1`을 상태로 남기지 않는다. 전투 종료 조건도 `!party.length`(전멸)뿐이다.
3. **조건 어휘에 "살아 있는 아군 수"가 없다.** `effectConditions`의 체력·정신력 조건은 대상 자신만 본다.
4. **시작 시점 판정 지점이 애매하다.** 1인 단독 출전은 `gameBegin` → `gameNext`(1라운드)에서 이미 확정돼 있으므로, 그때 상태를 만들고 3중첩을 부여해야 한다. 카드 사용 시점에만 판정하면 "시작부터 3중첩"이 늦게 적용된다.
5. **라운드 중 순서 문제.** 카드 사용은 5단계, 동료 사망은 6~7단계다. 같은 라운드에 동료가 죽고 내가 그 뒤에 카드를 쓰는 경우, 판정을 언제 하느냐에 따라 결과가 달라진다. 규칙을 정하고 문서·테스트로 고정해야 한다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 유닛 상태 `soloAwake` | `true`면 `[술래 각성]` |
| 유닛 상태 `allyLosses` | 이번 전투에서 쓰러진 아군 수(로그·표시용) |
| 유닛 상태 `soloSeeded` | 시작 시 3중첩을 이미 부여했는지(중복 방지) |
| 발동 시점 `allyDown` | `timings`·`passiveTimings` 등록. 쓰러진 유닛을 대상으로 발동 |
| 조건 `aloneAwake` | `flagConditions`에 등록(임계값 없는 체크박스) |
| flowStat `aliveAllies` | 살아 있는 아군 수(자기 포함) |

#### (c) 파일별 구현

**`worker/game.js`**

```js
const gamePartyAlive=b=>Object.values(b.units).filter(u=>!u.enemy&&gameAlive(u));
const gameSoloAwake=(b,u)=>!u.enemy&&gameAlive(u)&&gamePartyAlive(b).length===1;

function gameSyncSolo(b){
  for(const u of Object.values(b.units)){
    if(u.enemy||!gameAlive(u))continue;
    const awake=gameSoloAwake(b,u);
    if(awake===!!u.soloAwake)continue;
    u.soloAwake=awake;
    gameApplySoloTrait(u,awake);                 // §4.9
    if(awake){
      u.nextMove=Math.min(7,(u.nextMove||0)+2);  // 각성 진입 즉시 이동력 +2
      gameLog(b,u.name+' · 술래 각성 — 눈가리개가 풀렸습니다.');
      gamePose(b,u,'shift');
    }else gameLog(b,u.name+' · 술래 각성이 가라앉았습니다.');
  }
}

function gameAllyDown(b,fallen){
  b.shock={};
  for(const u of gamePartyAlive(b)){
    if(u===fallen)continue;
    const ctx=gameContext(u,{id:'event:allyDown',name:'아군 사망',effects:[]},[fallen]);
    gamePassives(b,u,'allyDown',fallen,ctx);      // 중첩/패시브 반응
  }

}
```

호출 지점:

1. `gameDamage`의 말미, `hp`가 0으로 떨어지는 순간:
   ```js

     gameLog(b,u.name+' 전투 불능');
   ```

   재귀(반사·반격 피해)로 여러 명이 동시에 쓰러져도 `gameSyncSolo`가 멱등이므로 안전하다.
2. `gameNext`에서 **전투 종료 분기(`return`) 뒤, 귀환 좌표 처리 앞**. 전투 종료 분기 안에 넣으면 승리/패배 시에도 상태를 건드리게 되고, `return` 이후에 두면 생존 파티 기준으로 확정된다:
   ```js
   gameSyncSolo(b);
   ```
   이 지점이 1라운드 시작(=`gameBegin` → `gameNext`)도 포함하므로 "1인 단독 출전이면 시작부터 각성"이 자동으로 성립한다.

#### (d) 엣지 케이스

1. **봇도 아군이다.** `party`는 `!u.enemy`인 생존 유닛 전부이므로 봇 1명이라도 살아 있으면 각성이 아니다. "혼자 연습(solo, bots:0)"이면 시작부터 각성이다.
2. **붕괴(개념화)는 사망이 아니다.** `gameConceptualize`는 `hp`를 0으로 만들지 않는다. 붕괴한 아군을 "살아 있는 아군"으로 셀지 결정해야 한다. **권장: 살아 있음으로 센다**(`hp>0` 기준). 붕괴자를 사망으로 치면 술래가 너무 쉽게 각성한다.
3. **동시 사망.** 광역 피해로 둘이 함께 쓰러지면 `gameAllyDown`이 두 번 호출되고 두 번째에서 `party.length===1`이 되어 각성이 켜진다. 순서 의존이 없도록 `gameSyncSolo`는 항상 전체를 재계산한다(부분 갱신 금지).
4. **각성 해제.** 부활 기믹이 없으므로 단방향이다. 나중에 부활이 생기면 `gameSyncSolo`가 자동으로 되돌린다(그래서 `else` 분기를 남겨 둔다).
5. **전투 종료 시.** 적이 죽어 승리하면 `gameNext`가 `phase='finished'`로 빠지므로 `gameSyncSolo`는 호출되지 않는다. 패배(전멸) 시에도 파티가 비어 아무 일도 일어나지 않는다.
6. **`allyDown` 발동 대상.** 이미 죽은 유닛은 `gamePassives`의 `gameAlive(actor)` 가드로 제외된다. 쓰러진 본인의 `struck` 반응은 `gameStrike`에서 이미 처리됐다.

### 4.7 기믹 7 — 각성 상태에 따른 동적 카드 스펙 오버라이드

대상: 술래 `숫자 세기`(비용 10→5, 위력 +6, 사거리 전장, 보호막 무시), `찾았다`(위력 +10, 확정 치명타, 30% 회복, 처치 시 유지).

#### (a) 왜 지금 구조에서 바로 안 되는가

카드의 수치(`cost`, `power`, `range`, `target`)는 **카드 객체에 고정**되어 있고, 엔진은 여러 지점에서 그 객체를 직접 읽는다.

| 읽는 지점 | 읽는 값 |
| --- | --- |
| `rules.js:cardUsable` | `card.concept && unit.mind < card.cost` |
| `worker/game.js:gameSelect` | `cardUsable`, `gameAllowedTargets`(사거리), 비용 오류 메시지 |
| `gamePrepareAction` | `if(card.cost) gameMental(b,u,-card.cost,true)` |
| `gameActionPower` / `gameHitSequence` | `cardHitPowers(ctx.card)` |
| `gameStrike` | `ctx.critical`, `gameDamage(...,piercing,...)` |
| `gameView` | `hand:[...library[id]]` 그대로 클라이언트로 전송 |
| `public/game.js` | `renderCardFace`, `powerBounds`, 손패 버튼 `disabled` 판정 |

**대안으로 `replaceCard`(다른 카드로 발동)를 쓸 수 없다.** `gameSelect`가 **원본 카드의 사거리**로 대상 유효성을 먼저 검증하고(`available=gameAllowedTargets(b,preview,card)`), `gameReplacement`는 그 뒤에 대상만 다시 고른다. 그래서 "사거리 1~3 → 전장 전체"처럼 **확장**하는 변경은 계획 단계에서 막힌다. 비용도 `gameSelect`가 원본으로 검사하므로, 정신력 7인데 각성 비용 5로 쓰는 상황을 표현할 수 없다.

#### (b) 필요한 데이터 스키마

```js
// 카드 프리셋
{
  id:'conceptTagStart', name:'술래잡기 · 숫자 세기', concept:true, generated:false,
  power:'2d6+5', range:'1~3', cost:10, effects:[...],
  states:{
    soloAwake:{
      cost:5,
      hitPowers:['2d6+11'],        // 위력 +6 (2d6+5 + 6)
      powerBonusLabel:'+6',
      range:'0~11',                // 전장 전체
      ignoreShield:true,           // 보호막 무시
      stateNote:'[술래 각성] 정신력 5 · 전장 전체 · 보호막 무시'
    }
  }
}
```

| 필드 | 뜻 |
| --- | --- |
| `states.<key>.cost` | 대체 정신력 비용 |
| `states.<key>.hitPowers` | 대체 위력 배열(`power`만 고치면 무효 — 아래 주의) |
| `states.<key>.range`, `rangeShape` | 대체 사거리 |
| `states.<key>.target` | 대체 대상 모드(선택) |
| `states.<key>.ignoreShield` | 이 카드의 타격이 보호막을 건너뛴다 |
| `states.<key>.guaranteedCrit` | 이 카드의 모든 타격이 치명타 |
| `states.<key>.stateNote` | UI 표시 문구 |

상태 키 결정 함수는 카드 상태(`requiredState`)와 섞지 않는다. 별도 함수로 둔다:

```js
const gameCardStateKey=unit=>unit?.soloAwake?'soloAwake':null;
```

#### (c) 파일별 구현

**`worker/game.js`** — 해석 함수 하나를 만들고 모든 읽기 지점을 그것으로 통과시킨다.

```js
function gameCardSpec(unit,card){
  if(!card?.states)return card;
  const key=gameCardStateKey(unit);
  const override=key&&card.states[key];
  if(!override)return card;
  return {...card,...override,specKey:key,
    ...(override.power&&!override.hitPowers?{hitPowers:[override.power]}:{})};
}
```

주의: `cardHitPowers = card => card.hitPowers ?? [card.power]`이다. **`hitPowers`가 있는 카드에서 `power`만 바꾸면 아무 효과가 없다.** 술래 카드는 단타지만 `hitPowers`를 명시했으므로 반드시 `hitPowers`를 덮어쓴다.

적용 지점(빠뜨리면 증상이 조용히 나타난다):

| 지점 | 변경 |
| --- | --- |
| `gameSelect` | `const spec=gameCardSpec(u,card)`; `cardUsable(u,spec)`, `gameAllowedTargets(b,preview,spec)`, 비용 메시지 `spec.cost` |
| `gamePrepareAction` | `const spec=gameCardSpec(u,original)`; `if(spec.cost)`; `ctx=gameContext(u,spec,targets,moved)`; `ctx.originId=original.id` 유지 |
| `gamePlanningEffects` | `cardUsable(unit,gameCardSpec(unit,card))` |
| `gameDeckEffects` | `cardUsable(actor,gameCardSpec(actor,card))` |
| `gameCardReactions` / `gameCover` | 동일하게 spec 경유 |
| `gameView` | 손패 직렬화 시 `{...gameCardSpec(unit,library[id])}` |
| `gameStrike` | `ctx.critical=roll>0&&(ctx.card.guaranteedCrit||actor.critCharges>0||chance>0&&...)`; `gameDamage(b,target,roll,actor,!!ctx.card.ignoreShield,true,false,origin)` |
| `gameFinishCard` | `ctx.originId`(원본 id) 기준이므로 그대로 |

`rules.js:cardUsable`은 손대지 않는다. 상태를 인자로 받게 만들면 순수 함수가 아니게 되고, 호출부 14곳이 함께 오염된다. **spec을 만들어 넘기는 방식**이 회귀 위험이 가장 낮다.

`gameContext`는 `mentalPower(actor.mind)`를 `mod`에 넣고 `card`를 그대로 보관하므로, `powerBonus` 같은 추가 필드는 쓰지 않는다(위력은 `hitPowers`로 이미 반영).

**`public/game.js`**

1. 손패 카드 얼굴과 미리보기에서 현재 상태의 수치를 보여준다. `state.battle`이 있으면 `self` 기준으로 `states[key]`를 덮어쓴다(서버가 이미 spec을 내려주므로 `hand` 항목을 그대로 쓰면 된다).
2. 카드 보관함/덱 화면에서는 두 상태의 수치를 함께 보여준다(전투 밖에서는 상태가 없으므로 원본 + `stateNote`).
3. `powerBounds`(최소·최대 위력 범위)가 spec의 `hitPowers`를 쓰도록 한다.

#### (d) 엣지 케이스

1. **비용 검증의 순서.** `gameSelect`가 원본 비용(10)으로 검증하면 정신력 7인 각성 상태 플레이어가 카드를 고를 수 없다. 반드시 spec 기준으로 검증한다(위 표).
2. **사거리 확장과 UI.** 플레이어가 먼 적을 클릭할 수 있어야 하므로 전장 하이라이트(`battlePanel`의 `paths`/타깃 표시)도 spec 사거리를 써야 한다. 서버가 `hand`에 spec을 실어 보내면 클라이언트의 `cardUsable`/`gameReach` 호출이 자동으로 맞는다(`public/game.js`는 `./grid.js`와 `./rules.js`를 직접 import한다).
3. **상태 전환 타이밍.** spec은 **사용 시점(5단계)** 에 확정된다. 같은 라운드에 동료가 늦게 죽으면 그 라운드의 카드는 평소 스펙이다. 이 규칙을 카드 문구에 명시한다.
4. **보호막 무시의 정확한 의미.** `piercing=true`는 보호막을 건너뛰지만 **피해 경감(`u.reduce`)은 적용**된다. "보호막 무시"와 일치한다. 보호막을 아예 지우는 효과(`stripShield`)와 혼동하지 않는다.
5. **확정 치명타를 `critCharges`로 구현하면 안 된다.** `critCharges`는 타격마다 1씩 소모되고 남으면 다음 카드로 이어진다. `ctx.card.guaranteedCrit` 플래그로 이 카드에만 적용한다.
6. **spec에 효과를 추가하지 않는다.** `actor.effectUsage`의 키가 `card.id + ':' + effects.indexOf(...)`이므로 spec에서 효과 배열을 바꾸면 인덱스가 밀려 발동 제한 카운터가 어긋난다. 상태별 추가 효과가 필요하면 **별도 카드**로 분리한다.
7. **전투 밖 화면.** `gameView`의 `defaults`(카탈로그)는 원본이므로, 카드 보관함에서 각성 수치를 보려면 `states`를 표시하는 UI 분기가 필요하다.

### 4.8 기믹 8 — 처치 시 소멸 면제와 쓰러진 아군 수 비례 고정 피해

대상: 술래 `찾았다`(쓰러진 아군 수 × 6 고정 피해, 처치 시 손패 유지).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **처치 여부로 목적지를 바꿀 수 없다.** `gameFinishCard`는 `ctx.destination` 문자열 하나만 본다(`'grave'|'hand'|'deckTop'|'deckBottom'|'exile'`). `condition:'foeDown'`(현재 대상 전투 불능)은 있지만, `{when:'end',kind:'exile'}`와 `{when:'end',kind:'return'}`을 나란히 두고 조건을 다는 방식은 **두 효과가 모두 실행되어 마지막 것이 목적지를 덮어쓰는** 순서 의존 코드가 된다. 효과 배열 순서가 바뀌면 조용히 깨진다.
2. **"쓰러진 아군 수" 통계가 없다.** `flowStats`에 해당 항목이 없어 `amountExpr`로 비례 피해를 만들 수 없다.
3. **`perStack`류의 비례 효과는 중첩 소모에 묶여 있다.** 아군 수는 중첩이 아니라 전장 상태다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 카드 필드 `exhaustUnlessKill` | `true`면 처치 시 손패로, 아니면 소멸 |
| flowStat `deadAllies` | 이번 전투에서 쓰러진 아군 수(자기 제외) |
| ctx 필드 `killedFoe` | 이 카드로 적을 쓰러뜨렸는가 |

> 이 필드는 뒤에서 **범용 `keepOn` + `keepDestination`으로 일반화한다**(§4.13). 「세계의 분해자」의 '5중첩이면 덱 복귀'가 두 번째 사례가 되면서 카드별 하드코딩은 유지비가 더 커진다. 구현 시점에 §4.13의 형태로 한 번에 만드는 편이 좋다.

카드 효과:

```js
{when:'hit',kind:'fixedDamage',to:'target',
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'deadAllies'},{type:'number',value:6}]}},
{when:'damage',kind:'hitLeech',to:'self',amount:30}
```

#### (c) 파일별 구현

**`worker/game.js`**

1. 처치 플래그. `gameHitSequence`의 `strike` 안, 피해 적용 직후:
   ```js
   const dealt=gameStrike(b,ctx,target,roll);
   if(dealt!==null&&target.enemy!==ctx.actor.enemy&&!gameAlive(target))ctx.killedFoe=true;
   ```
2. 목적지 분기. `gameFinishCard` 맨 앞:
   ```js
   const u=ctx.actor,id=ctx.originId||ctx.card.id;
   ```

   ```js
     .filter(u=>u!==actor&&u.enemy===actor.enemy&&u.hp<=0).length;
   ```
   `actor.enemy` 기준이므로 봇과 플레이어를 모두 아군으로 센다.
4. `public/rules.js`의 `flowStats`에 `deadAllies:'쓰러진 아군 수'` 추가.

#### (d) 엣지 케이스

1. **손패가 12장이면 유지 불가.** 묘지로 보내고 로그를 남긴다. 카드 문면("손패에 그대로 남는다")과 충돌하므로, 상한을 예외로 두지 말고 로그로 명시한다.
2. **다중 타격·광역에서 다른 적이 죽은 경우.** `ctx.killedFoe`는 카드 단위 플래그이므로 "이 카드로 아무 적이나 처치"를 뜻한다. 주 대상만 인정하려면 `targets[0]`을 비교한다.
3. **반사·지속 피해로 죽은 경우.** 그 피해는 다른 origin이므로 이 카드의 플래그가 서지 않는다.
4. **승리 직후.** 적이 죽으면 9단계 `gameFinishCard`가 먼저 실행되고, 15단계 `gameNext`에서 전투가 끝난다. 따라서 "처치 시 손패 유지"가 정상 동작한다. 다만 전투가 끝나면 손패는 새 전투에서 의미가 없다.
5. **`deadAllies`가 0이면.** `amountExpr` 결과가 0이라 효과가 발동하지 않는다(`if(!n)return`). 로그도 남지 않는다.
6. **붕괴한 아군.** `hp>0`이므로 세지 않는다(§4.6의 권장과 일관).

### 4.9 기믹 9 — 상태에 따라 중첩 효과가 동적으로 바뀌는 스케일링

대상: `술래의 눈`(평소: 중첩당 주는 피해 +5% / 받는 피해 −5%, 각성: 중첩당 주는 피해 +20%, 치명타 +10%p, 이동력 +2, 턴 시작 정신력 +6).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **중첩 정의는 최초 부여 시 1회만 등록된다.** `gameGrantStacks`의 `if(trait && !unit.stackTraits?.[tag]) unit.stackTraits[tag]=trait`. 이후에는 다른 정의를 넘겨도 무시된다.
2. **효과 수치는 정적이다.** `conceptStacks`의 `amount`를 상태에 따라 바꾸는 장치가 없다. `scaleStack`은 중첩 수만 곱한다.
3. **`held`로 표현 가능한 종류가 제한된다.** `heldStackEffectKinds`에 `outgoingDamage`·`incomingDamage`·`critChance`는 있으므로 피해·치명타는 되지만, **이동력과 정신력 회복은 `held`로 표현할 수 없다**(`nextMove`·`mind`는 `held` 목록에 없고, `gameHeldModifiers`가 계산하지도 않는다). 따라서 턴 시작 시점 효과로 처리해야 한다.
4. **중첩 수는 유지한 채 정의만 바꿔야 한다.** 상태 전환 시 중첩을 새로 부여하면 상한·획득 원장(`stackAcquisitions`)·소모 우선순위(`stackRuns`)가 어긋난다.

#### (b) 필요한 데이터 스키마

태그는 하나(`'술래의 눈'`), 정의는 두 벌:

```js
const SOLO_CALM={name:'술래의 눈',cap:3,concept:true,
  description:'중첩당 주는 피해 +5%, 받는 피해 −5%.',effects:[
    {when:'held',kind:'outgoingDamage',to:'self',amount:5,amountMode:'percent',scaleStack:'count'},
    {when:'held',kind:'incomingDamage',to:'self',amount:-5,amountMode:'percent',scaleStack:'count'}
  ]};
const SOLO_AWAKE={name:'술래의 눈',cap:3,concept:true,
  description:'각성 — 중첩당 주는 피해 +20%, 치명타 +10%p, 이동력 +2, 턴 시작 정신력 +6.',effects:[
    {when:'held',kind:'outgoingDamage',to:'self',amount:20,amountMode:'percent',scaleStack:'count'},
    {when:'held',kind:'incomingDamage',to:'self',amount:-5,amountMode:'percent',scaleStack:'count'},
    {when:'held',kind:'critChance',to:'self',amount:10},
    {when:'turnStart',kind:'nextMove',to:'self',amount:2},
    {when:'turnStart',kind:'mind',to:'self',amount:6}
  ]};
```

#### (c) 파일별 구현

**`worker/game.js`**

```js
function gameApplySoloTrait(unit,awake){
  if(!(unit.stacks['술래의 눈']>0))return;
  unit.stackTraits['술래의 눈']={...(awake?SOLO_AWAKE:SOLO_CALM)};
  unit.stackCaps??={};unit.stackCaps['술래의 눈']=3;
}
```

호출 지점:

1. `gameSyncSolo`에서 상태가 바뀔 때(§4.6).
2. `gameGrantStacks`의 **부여 성공 경로 마지막**. `gameConceptStack`이 넘기는 정의는 정적이므로, 부여가 끝난 뒤 상태에 맞게 교체한다. 초기 반환(`if(!gained)return 0;`, `if(!count)return 0;`)에는 걸리지 않도록, `(unit.stackCaps??={})[tag]=cap;` 바로 다음 줄에 둔다:
   ```js
   (unit.stackCaps??={})[tag]=cap;
   if(tag==='술래의 눈')gameApplySoloTrait(unit,!!unit.soloAwake);
   ```
3. `cleanseStacks`/`remove`로 0이 된 뒤 재부여되는 경로도 2번에서 자동 처리된다.

**이동력 +2의 중복 방지.** 각성 진입 시 `nextMove += 2`(§4.6)와 각성 정의의 `turnStart nextMove +2`가 겹치면 진입 라운드에 +4가 된다. 규칙을 정한다.

- **권장:** 진입 시 즉시 +2(이번 라운드 이동력), 그리고 `turnStart`의 +2는 **다음 라운드** 이동력이다. 진입 라운드의 `turnStart`는 이미 지나갔으므로 중복이 아니다. 단, 진입이 라운드 시작 직후(15단계)일 때 `turnStart` 효과가 아직 남아 있으면 같은 라운드에 +4가 될 수 있으므로, `gameSyncSolo`에서 진입 시점을 `b.resolving`으로 구분해 `b.resolving`이면 `turnStart` 가산을 건너뛴다.

**정신력 +6.** `turnStart`의 `mind` 효과는 `gameDeckEffects('turnStart')`에서 보유 중첩 소스로 발동한다. `gameMental`이 100에서 자르므로 초과분은 사라진다.

**`public/game.js`**

1. 중첩 칩 툴팁에 현재 정의와 **다른 상태의 정의**를 함께 보여준다. `stackEffectText`는 `u.stackTraits[name].effects`만 읽으므로, `public/game.js`에 두 벌을 넣어 "각성 시: …" 줄을 덧붙인다.
2. 카드 얼굴의 중첩 미리보기(`renderCardFace`의 `byStack`)는 `conceptStacks`를 읽는다. 여기에도 각성 문구를 넣어야 사용자가 카드만 보고 효과를 이해한다.

#### (d) 엣지 케이스

1. **정의 교체 시점.** 라운드 중간(피해 계산 도중)에 교체하면 같은 피해에 두 정의가 섞일 수 있다. `gameSyncSolo`는 라운드 경계(사망 직후·`gameNext`)에서만 호출한다.
2. **`incomingDamage` −5%는 각성에서도 유지.** 카드 문면이 "평소 … 받는 피해 −5%"이고 각성 문면에는 받는 피해가 없다. 각성에서 −5%가 사라지는 것으로 읽는 것이 자연스럽다면 `SOLO_AWAKE`에서 그 항목을 빼야 한다. **문면 재확인 필요**(현재 이 문서는 유지로 적었다).
3. **`outgoingDamage` 중첩 배율의 상한.** 3중첩 각성 = +60%. `applyPowerRatio`가 퍼센트를 곱하므로 수치가 커진다. 상한(`bounded(...,-999,999)`)은 넘지 않는다.
4. **역전된 부호.** `incomingDamage`의 음수 퍼센트는 `gameDamage`의 `ratios` 합산에서 마이너스로 들어가 피해를 줄인다. `amountMode:'percent'` + `scaleStack:'count'` 조합이 기존 '귀환의 문턱'과 동일하므로 안전하다.
5. **다른 유닛이 같은 태그를 얻은 경우.** 태그가 전장 공용 이름이므로 적이 '술래의 눈'을 얻으면 `gameConceptTraits` 기준 정의가 쓰인다. 정의 교체는 보유자 단위(`unit.stackTraits`)이므로 서로 영향을 주지 않는다.
6. **전투 종료 정리.** `gameNext`가 `trait.concept`인 중첩을 정리하므로 두 정의 모두 `concept:true`를 유지한다.

### 4.10 기믹 10 — 시전자 자해 리스크와 역류 반동

대상: 세계의 분해자(`점액 덮기`, `완전 소화`).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **보호막 전량 제거는 이미 된다.** `stripShield`는 `gameRemoveShield(u,n)`을 호출하고 `n`에 큰 값을 주면 전량 제거된다(임시 보호막도 함께 깎인다). `to:'self'`로 두면 자기 보호막이 대상이므로 "사용 시 시전자 자신의 보호막도 전부 제거"가 **새 코드 없이** 표현된다.
   ```js
   {when:'use', kind:'stripShield', to:'self', amount:999}
   ```
2. **역류 판정의 재료가 없다.** "빗나갔거나 제거한 중첩이 2개 이하"를 판정하려면 (i) 이번 카드가 실제로 제거한 중첩 수, (ii) 적중 여부가 필요하다. 적중 여부는 `hit` 시점이 발동했는지로 알 수 있지만, **빗나가면 `hit` 시점 자체가 발동하지 않으므로** "빗나감"을 직접 관측할 훅이 없다.
3. **해결의 실마리: `end` 시점은 빗나가도 발동한다.** `gameFinishCard`가 `gameTriggers(b,ctx,'end',...)`를 무조건 호출하기 때문이다. 즉 `end` 시점에 "제거 수 ≤ 2"를 조건으로 걸면 **빗나감(0)과 2개 이하를 하나의 분기로** 처리할 수 있다. 다만 조건이 `ctx`의 제거 수를 읽어야 하는데, `gameEffectCondition`의 조건은 대부분 `u`(대상) 기준이고 ctx 기반 조건은 `moved`·`brokeShield`·`clashMargin` 등 몇 개뿐이다.
4. **제거 수를 ctx에 남기는 효과가 없다.** `clearAllStacks` 자체가 없기 때문이다(§4.12). 두 기믹은 함께 구현해야 한다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| ctx `removedStacks` | 이번 카드가 제거한 중첩 **개수** 합 |
| ctx `removedPotency` | 제거한 중첩의 **총 위력** 합(로그·표시용) |
| ctx `flags: Set` | `'killedFoe'`, `'maxDissolve'` 같은 판정 플래그의 공통 저장소 |
| 조건 `removedStacksMax` | `(ctx.removedStacks||0) <= threshold` |

카드 효과:

```js
{when:'use', kind:'stripShield', to:'self', amount:999},                                   // 내 보호막 전량 제거
{when:'hit', kind:'clearAllStacks', to:'target'},                                           // §4.12
{when:'end', kind:'stack', to:'self', amount:2, tag:'용해',
 condition:'removedStacksMax', threshold:2}                                                 // 역류
```

#### (c) 파일별 구현

**`worker/game.js`**

1. `gameContext`에 `flags:new Set()`을 추가한다(§4.13과 공유).
2. `gameEffectCondition`에 ctx 기반 조건을 추가한다. 기존 ctx 조건(`moved`, `brokeShield`, `criticalSpent`)과 같은 자리에 둔다.
   ```js
   case 'removedStacksMax': return (ctx.removedStacks||0)<=n;
   ```
3. `clearAllStacks`가 `ctx.removedStacks`를 채운다(§4.12).
4. 효과 배열 순서가 계약이다. `gameTriggers`는 같은 시점의 효과를 **배열 순서대로** 실행하므로, `stripShield`(use) → `clearAllStacks`(hit) → 역류(end) 순서가 자연스럽다.
5. `gameFinishCard`는 `end` 시점을 먼저 발동하고 그 뒤 목적지를 결정한다. 따라서 역류로 부여된 중첩이 소멸 처리에 영향을 주지 않는다(정상).

**`public/game.js`** — `effectSentence`에 "제거한 중첩 2개 이하이면" 문구를 추가한다.

#### (d) 엣지 케이스

1. **보호막이 0일 때.** `gameRemoveShield`가 0을 돌려주므로 로그가 남지 않는다. 리스크 없이 쓰는 것이므로 정상이다.
2. **회피(`dodge`)로 빗나간 경우.** `gameStrike`가 `null`을 돌려주고 `hit` 시점이 발동하지 않는다 → `removedStacks`가 0 → 역류 발동. 의도와 일치한다.
3. **이동으로 사거리를 잃은 경우.** `gameHitSequence`의 `canStrike()`가 false면 타격 자체가 없다 → 같은 경로로 역류.
4. **적이 죽어서 전투가 끝난 경우.** `end` 시점은 정상 발동하므로 역류 중첩이 붙는다. 전투가 끝나면 의미는 없지만 오류가 없어야 한다.
5. **역류 중첩의 즉시 피해.** `용해`는 `turnEnd`에 피해를 준다. 이미 지난 턴이므로 다음 라운드 종료에 6 피해가 들어온다.
6. **`stripShield`의 수치 상한.** `stripShield`의 `maximum`은 `Infinity`라 999가 그대로 전달된다. 보호막 상한이 999이므로 전량 제거와 동치다.

#### (e) 회귀 테스트

```js

test('a missed finisher or a finisher removing two marks or fewer rebounds onto the caster', async()=>{ ... });
test('a finisher that removes three or more marks does not rebound', async()=>{ ... });
```

### 4.11 기믹 11 — 회복·보호막 획득량 감쇠 (onHeal / onGainShield)

대상: `용해`(중첩당 회복·보호막 −20%, 5중첩이면 100%).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **회복 감소는 있다. 그러나 중첩으로는 없다.** `healCut`(받는 회복량 감소)은 `u.healCuts` 배열에 `{amount, through}`로 쌓이는 **시간제 상태**이고, `gameHeal`이 `Math.max(...healCuts)`를 페널티로 쓴다. `heldStackEffectKinds`에 없으므로 "보유 중인 중첩이 회복을 깎는다"는 표현이 불가능하다.
2. **보호막 획득 감소는 아예 없다.** `gameHeal`에 해당하는 단일 창구가 없고, 보호막을 늘리는 지점이 **10곳**에 흩어져 있다.

   | 지점 | 의미 |
   | --- | --- |
   | `case 'shield'` | 기본 보호막 |
   | `case 'rallyShield'` | 아군 전원 보호막 |
   | `case 'shieldPerStack'` | 중첩 소모 연계 보호막 |
   | `case 'temporaryShield'` | 이번 라운드 보호막 |
   | `case 'stealShield'` / `case 'shieldGift'` | 보호막 이전 |
   | `case 'debtShield'` | 유예 피해 전환 |
   | `case 'graveToShield'` | 묘지 카드 → 보호막 |
   | `gameResolve`의 `u.nextShield` | 다음 라운드 예약 보호막 |
   | `gameApplyConversion`의 `shield`/`temporaryShield` | 생명력 흡수·방어막 변환 |

3. **100% 클램프가 필요하다.** 5중첩에서 100% 감소면 획득 0이다. `Math.min(100, …)`를 빠뜨리면 음수 감소율이 되어 회복이 오히려 늘어난다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| `heldStackEffectKinds` | `'healCut'`, `'shieldGainCut'` 추가 |
| 효과 `shieldGainCut` | "받는 보호막 획득량 감소". `amountMode:'percent'`, `scaleStack:'count'` 지원 |
| 단일 창구 `gameGainShield(b,u,amount,{temporary})` | 보호막 획득의 유일한 경로 |

중첩 정의:

```js
'용해': {cap:5, description:'턴 종료마다 중첩×3 고정 피해. 얻는 체력 회복·보호막이 중첩당 20% 감소.', effects:[
  {when:'turnEnd', kind:'fixedDamage', to:'self', amount:3, scaleStack:'count'},
  {when:'held', kind:'healCut', to:'self', amount:20, amountMode:'percent', scaleStack:'count'},
  {when:'held', kind:'shieldGainCut', to:'self', amount:20, amountMode:'percent', scaleStack:'count'}
]},
```

#### (c) 파일별 구현

**`public/rules.js`**

1. `heldStackEffectKinds = [...,'weaken','healCut','shieldGainCut']`(§4.2에서 `weaken` 추가).
2. `newEffects.shieldGainCut=['보호막 획득량 감소','use','self','받는 보호막 획득량 {n}% 감소']`. `ratioEffects`에도 `shieldGainCut:['보호막 획득 감소',-1,'피해 판정',true]` 형태로 등록해 퍼센트 부호 처리를 맞춘다.

**`worker/game.js`**

1. `gameHeldModifiers`는 `amountMode==='percent'`면 키를 `kind+'Percent'`로 만든다. 즉 읽을 때는 `held.healCutPercent`, `held.shieldGainCutPercent`를 쓴다(원인별 키 이름을 혼동하지 않는다).
2. `gameHeal`의 페널티 계산:
   ```js
   const held=gameHeldModifiers(b,u,null);
   const penalty=Math.min(100,Math.max(0,
     ...(u.healCuts||[]).map(entry=>entry.amount),
     held.healCutPercent||0));
   ```
   기존 코드는 `Math.max`만 썼다. **합산(`+`)으로 바꾸면 기존 healCut 저주와 겹칠 때 동작이 바뀌므로**, 기존 테스트(`life steal …`, `healCut` 관련)를 확인한 뒤 결정한다. 권장: 기존 `healCuts`는 `max`, 중첩 감쇠는 합산 후 100 클램프.
3. 보호막 단일 창구:
   ```js
   function gameGainShield(b,u,amount,{temporary=false}={}){
     if(!gameAlive(u)||amount<=0)return 0;
     const held=gameHeldModifiers(b,u,null);
     const cut=Math.min(100,Math.max(0,held.shieldGainCutPercent||0));
     const gained=Math.min(999-u.shield,Math.floor(amount*(100-cut)/100));
     if(gained<=0)return 0;
     u.shield+=gained;
     if(temporary)u.temporaryShield=(u.temporaryShield||0)+gained;
     return gained;
   }
   ```
   10곳을 이 함수로 교체한다. **보호막 이전(`stealShield`, `shieldGift`)은 감쇠 예외**로 둘 것을 권장한다(획득이 아니라 이동이므로).
4. `nextShield`(예약 보호막)는 지급 시점(다음 라운드 종료)에 `gameGainShield`를 쓴다. 예약할 때 깎으면 그 사이 중첩이 바뀌었을 때 결과가 어긋난다.

#### (d) 엣지 케이스

1. **`drainLife`, `lifeSteal`, `hitLeech`, `regen`, `healPercent`, `healMissing`은 모두 `gameHeal`을 거친다** → 자동으로 감쇠가 적용된다. 별도 수정이 필요 없다는 점을 테스트로 고정한다.
2. **회복 0 로그.** `gameHeal`은 `healed`가 0이면 로그를 남기지 않는다. 5중첩 상태에서 회복 카드를 쓰면 아무 일도 안 일어난 것처럼 보이므로, "회복량 100% 감소" 로그를 한 번 남기는 편이 좋다.
3. **임시 보호막.** `temporaryShield`와 `shield`는 같은 풀에서 깎이므로(`gameRemoveShield`) 감쇠는 지급 시점에만 적용한다.
4. **상한 999.** `Math.min(999-u.shield, …)`를 유지한다.
5. **`shieldGift`의 대상.** 이전받는 쪽이 `용해` 5중첩이면 이전량이 0이 될 수 있다. 예외로 두면 그런 상황이 없다.
6. **감쇠와 `shieldWard`류.** 부여 저항(`stackWard`)은 중첩 부여에만 관여하므로 무관하다.

#### (e) 회귀 테스트

```js
test('dissolve marks cut healing and shield gain by twenty percent per mark and block them at five', async()=>{ ... });
test('life steal and regen healing are cut by dissolve marks as well', async()=>{ ... });
test('shield transfers are not reduced by dissolve marks', async()=>{ ... });
```

### 4.12 기믹 12 — 대상의 모든 중첩 일괄 제거와 제거 수 비례 고정 피해

대상: `완전 소화`(모든 중첩 제거, 제거 수×6 고정 피해, 절반 회복).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **`cleanseStacks`는 태그 하나만 지운다.** `gameWriteStacks(u,tag,[])` + `delete u.stacks[tag]`. 전장의 "모든 중첩(버프·디버프 불문)"을 지우는 효과가 없다.
2. **제거 총량을 남기지 않는다.** `gameTakeStacks`는 위력을 반환하지만 ctx에 저장하지 않는다. `perStack`류는 `consume` 시점의 `ctx.usedPotency`만 본다.
3. **제거 수 기준 피해를 계산할 통계가 없다.** `amountExpr`로 쓰려면 `flowStats`에 항목이 있어야 한다.
4. **순서 계약이 필요하다.** "제거 → 제거 수 계산 → 피해 → 보너스 판정"이 한 시점 안에서 순서대로 일어나야 한다. 같은 시점 효과는 배열 순서대로 실행되므로 **카드 효과 배열이 계약**이 된다.

#### (b) 필요한 데이터 스키마

| 추가 | 내용 |
| --- | --- |
| 효과 `clearAllStacks` | 필드 `excludeTags?(string[])`, `countMode?('count'|'potency')` |
| ctx `removedStacks`, `removedPotency` | §4.10과 공유 |
| flowStat `removedStacks` | `ctx.removedStacks` |

카드 효과(배열 순서가 곧 실행 순서):

```js
{when:'hit', kind:'clearAllStacks', to:'target'},
{when:'hit', kind:'fixedDamage', to:'target',
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'removedStacks'},{type:'number',value:6}]}},
{when:'hit', kind:'heal', to:'self',
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'removedStacks'},{type:'number',value:3}]}}
// 최대 체력 20% 보너스는 별도 효과이며 keepOn 플래그(§4.13)로 조건을 건다
{when:'hit', kind:'fixedDamage', to:'target', condition:'maxDissolve',
 amountExpr:{op:'multiply',terms:[{type:'stat',stat:'targetMaxHp'},{type:'percent',value:20}]}}
```

절반 회복은 "고정 피해의 절반" = `removedStacks × 6 / 2` = `removedStacks × 3`이다. 정신력 회복은 넣지 않는다.

#### (c) 파일별 구현

**`worker/game.js`**

```js
case 'clearAllStacks': {
  if(!gameAlive(u))break;
  if((u.stacks['용해']||0)>=5)ctx.flags.add('maxDissolve');   // 제거 전에 판정
  let count=0,potency=0;
  for(const tag of Object.keys(u.stacks)){
    if(!(u.stacks[tag]>0)||effect.excludeTags?.includes(tag))continue;
    count+=u.stacks[tag];
    potency+=stackPotency(u,tag);
    gameTakeStacks(u,tag,u.stacks[tag]);
  }
  ctx.removedStacks=count;ctx.removedPotency=potency;
  if(count)gameLog(b,actor.name+' · '+u.name+' 중첩 '+count+' 제거 · 총 위력 '+potency);
  break;
}
```

주의:

- `Object.keys`는 스냅샷이므로 순회 중 `delete u.stackTraits[tag]`가 안전하다.
- `gameTakeStacks`는 `gameSplitStacks`로 오래된 부여부터 소모하고, 0이 되면 `gameWriteStacks`가 trait를 지운다 → `held` 보정이 즉시 사라진다(용해의 회복 감쇠도 함께 사라진다. 제거 후 회복이 정상 동작하는지 테스트로 확인).
- `flowStats.removedStacks` + `gameFlowValue`의 `case 'removedStacks': return ctx.removedStacks||0;`

**`public/rules.js`** — `newEffects.clearAllStacks`, `flowStats.removedStacks`, `effectConditions`에 필요한 플래그 조건(§4.13의 `maxDissolve`) 추가.

#### (d) 엣지 케이스

1. **"중첩 수"는 개수다.** `stackPotency`(개수×위력)와 다르다. 피해는 개수 기준, 로그에는 둘 다 남긴다.
2. **'용해'도 제거 대상이다.** 5중첩 보너스를 받은 뒤 그 용해가 사라지므로, 보너스 판정은 반드시 제거 **전**에 한다(`ctx.flags`).
3. **제거 후 대상이 죽는 경우.** `gameDamage`가 처리한다. 절반 회복은 시전자에게 가므로 사망과 무관하다.
4. **"절반"의 반올림.** `removedStacks × 3`은 정수다. 다른 카드에서 6/2가 홀수 상황을 만들려면 `Math.floor`를 명시한다.
5. **적이 중첩이 하나도 없을 때.** `count=0` → 피해 0 → 회복 0 → 역류 조건(≤2) 참 → 자기에게 용해 2. 빗나감과 같은 결과다.
6. **`fixedDamage`는 보호막에 막힌다.** "고정 피해"는 피해 경감·무시를 건너뛰지만 보호막은 적용된다. 보호막을 다 벗긴 시동 카드와의 조합이 의도대로인지 확인한다.
7. **제거가 `consume` 시점을 발동시키지 않는다.** `consume` 시점은 `consume` 효과 전용이다. "중첩이 제거될 때"에 반응하는 카드가 필요하면 `stackRemoved` 시점을 새로 만들어야 한다(현재 범위 밖).

#### (e) 회귀 테스트

```js

test('the finisher heals the caster for half of the fixed damage it dealt', async()=>{ ... });
test('removed marks no longer reduce the caster healing after they are gone', async()=>{ ... });
```

### 4.13 기믹 13 — 최대 체력 비례 추가 피해와 조건부 소멸 면제

대상: `완전 소화`의 5중첩 보너스(최대 체력 20% 추가 고정 피해, 소멸 면제 후 덱 복귀).

#### (a) 왜 지금 구조에서 바로 안 되는가

1. **최대 체력 20%는 이미 표현된다.** `amountExpr`에 `{type:'stat',stat:'targetMaxHp'}`와 퍼센트 노드를 곱하면 `Math.trunc(maxHp × 20 / 100)`이 나온다. `gameApplyEffect`가 `amountExpr` 결과에 `Math.trunc`를 적용하기 때문이다. **새 효과 종류를 만들 필요가 없다.**
2. **조건부 소멸 면제는 카드별 하드코딩이다.** §4.8에서 `exhaustUnlessKill`을 제안했지만, 분해자는 조건이 '처치'가 아니라 '5중첩'이고 목적지도 '손패'가 아니라 '덱 위'다. 카드마다 필드를 늘리면 `gameFinishCard`가 분기 지옥이 된다.
3. **"제거 전에 5중첩이었는가"를 알아야 한다.** 제거 후에는 알 수 없으므로 `clearAllStacks`가 플래그를 세워야 한다(§4.12).
4. **덱 복귀와 소멸 봉인이 충돌한다.** `exhaust` 처리에서 `u.purged`에 넣으면 이후 재획득이 막힌다. 면제 경로는 `purged`를 건드리지 않아야 한다.

#### (b) 필요한 데이터 스키마

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `keepOn` | `['killedFoe']`, `['maxDissolve']` | 이 플래그가 서면 소멸하지 않는다(OR) |
| `keepDestination` | `'hand'`(기본) / `'deckTop'` | 면제 시 목적지 |

`ctx.flags`는 `Set`으로 두고, `gameHitSequence`가 `'killedFoe'`, `clearAllStacks`가 `'maxDissolve'`를 넣는다.

카드 필드 예:

```js
// 술래 · 찾았다
{exhaust:true, keepOn:['killedFoe'], keepDestination:'hand'}
// 분해자 · 완전 소화
{exhaust:true, keepOn:['maxDissolve'], keepDestination:'deckTop'}
```

#### (c) 파일별 구현

**`worker/game.js`**

```js

    gameLog(b,u.name+' · 「'+ctx.card.name+'」 소멸 면제');

  }

  ...기존 목적지 분기

```

플래그를 세우는 곳:

```js

// clearAllStacks 안 (제거 전)
```

#### (d) 엣지 케이스

1. **덱 복귀와 `purged`.** 면제 경로에서 `purged`에 넣지 않는다. 넣으면 `reclaim`/`recycleExile`이 막혀 카드가 영영 돌아오지 못한다.
2. **손패 12장.** `keepDestination:'hand'`면 묘지로, `'deckTop'`이면 덱 상한이 없으므로 그대로 올린다.
3. **`maxDissolve`와 5중첩의 시점.** `clearAllStacks`가 제거 전에 판정한다. 대상이 4중첩이면 플래그가 서지 않는다.
4. **다중 대상 카드.** `clearAllStacks`가 여러 대상에게 적용되면 마지막 대상의 판정이 남는다. 단일 대상 카드에서는 문제 없지만, 광역으로 확장할 때는 `ctx.flags`를 대상별로 나눠야 한다(현재 범위 밖).
5. **전투 종료.** 적이 죽어 전투가 끝나도 `gameFinishCard`는 먼저 실행되므로 덱 복귀가 일어난다. 새 전투에서는 덱이 다시 만들어지므로 무해하다.
6. **20% 피해의 반올림.** `Math.trunc`이므로 2.9는 2가 된다. 최대 체력 54(적)면 10이다.

#### (e) 회귀 테스트

### 5.8 등록 지점 체크리스트 (어휘 하나를 추가할 때)

효과 종류를 추가하면:

1. `rules.js:newEffects` 또는 `effects` — 편집기 라벨.
2. `rules.js:taggedEffects` — 중첩 선택 UI가 필요할 때.
3. `rules.js:unnumberedEffects` — 수치가 없는 효과.
4. `rules.js:passiveEffectKinds` — 패시브에서도 쓸 때.
5. `worker/game.js:gameApplyEffect` switch.
6. `worker/game.js:gameApplyEffect`의 **once 목록** — `to:'self'`이고 `when:'consume'`이면 `!['perStack','consumeHeal','shieldPerStack']` 목록에 새 kind를 반드시 추가한다. 빠뜨리면 첫 번째 대상에게만 적용되고 조용히 끝난다(`mindPerStack`이 정확히 이 함정에 해당).
7. `public/game.js:effectFamilies`와 `effectSentence` — 제작기 그룹핑과 문장.

조건을 추가하면:

1. `rules.js:effectConditions` — 라벨.
2. `rules.js:flagConditions` — 임계값이 없으면 여기(체크박스 UI).
3. `rules.js:replacementConditions` — `replaceCard` 조건으로도 쓸 때.
4. `worker/game.js:gameEffectCondition` switch.

수신자를 추가하면:

1. `rules.js:effectRecipients` — 라벨.
2. `worker/game.js:gameEffectRecipients` switch.
3. `worker/game.js:gameApplyEffect`의 `to==='target'/'self'` 분기와 겹치지 않는지 확인.

카드 참조 필드를 추가하면:

1. `rules.js:cardReferenceFields` — `mapEffectCardReferences`가 리맵한다.
2. `worker/game.js:gameShareBundle` — 의존 카드 자동 포함.

카드 필드를 추가하면:

1. `worker/game.js:gameCard` — 외부 저장 카드의 검증·정규화(화이트리스트가 아니면 통과하지만, 값 범위 검증은 직접 추가).
2. `worker/game.js:gameView` — 클라이언트로 보낼지, `unit` 구조 분해에서 제외할지 결정.
3. `public/game.js:renderCardFace` / `cardLibraryFilter` / 덱 편성 — 표시·필터.

## 8. 신규 개념물 추가 시 갱신 체크리스트

새 개념물 설정을 승인받으면 코드 작성 전에 이 순서로 점검한다.

**설정 정리**

- [ ] 카드 수와 덱 편성 방식(시동 1장 + 생성 n장 / 독립 카드)을 정했다.
- [ ] 전용 중첩의 상한, 지속 조건(소모·제거·전투 종료), 발동 시점을 표로 정리했다.
- [ ] 각 카드의 위력·정신력·사거리·타수를 수치로 확정했다.
- [ ] 문면이 모호한 지점(중첩당인지 고정인지, 대상이 주 대상인지 시전자인지)을 명시했다.

**엔진 판정**

- [ ] §3.1 표로 "이미 되는 것"을 최대한 재사용했다.
- [ ] §3.2 표에서 걸리는 결손 번호를 모두 적었다.
- [ ] 각 결손에 대해 §4의 기믹 절을 새로 만들거나 기존 절을 확장했다.

**구현**

- [ ] §5.8 등록 지점을 모두 통과했다(효과·조건·수신자·참조 필드·카드 필드).
- [ ] 새 효과가 `to:'self'`+`when:'consume'`이면 once 목록에 추가했다.
- [ ] 새 카드 필드는 `gameCard` 검증과 `gameView` 전송 여부를 결정했다.
- [ ] 생성 카드는 `generated:true`, 덱 편성 차단, `temporary` 미사용을 확인했다.
- [ ] 중첩 정의를 상태에 따라 바꾸는 경우 교체 시점을 라운드 경계로 제한했다.
- [ ] 봇(`gameBotPlan`)이 새 카드/새 입력을 만나도 예외 없이 계획을 세운다(새 입력은 기본값으로 대체).
- [ ] 시전자 자해 리스크는 `stripShield`+`to:'self'`로 표현하고, 역류·반동 조건은 `end` 시점 + ctx 조건으로 만든다(빗나감도 같은 분기).
- [ ] 회복·보호막 획득 감쇠는 `gameHeal`과 `gameGainShield` 두 창구만 고친다(10곳 직접 수정 금지).
- [ ] 전체 중첩 제거는 제거 **전**에 보너스 플래그를 세우고, 효과 배열 순서를 테스트로 고정한다.
- [ ] 소멸 면제는 `keepOn`/`keepDestination`으로만 구현하고, 면제 경로에서 `purged`를 건드리지 않는다.

**표시**

- [ ] 카드 얼굴에 개념물·시동/생성·소멸·상태별 수치가 보인다.
- [ ] 중첩 칩 툴팁에 현재 정의와 상태별 문구가 보인다.
- [ ] 전장 하이라이트(끝줄·모서리)와 계획 입력(밀기/끌기)이 있다.
- [ ] 전투 로그에 발동·소모·환급이 남는다.

**검증**

- [ ] 기믹마다 회귀 테스트를 추가했다(§7 표에 행 추가).
- [ ] `npm test` 전체 통과, 브라우저 확인 항목 통과.
- [ ] 이 문서(§4.0 표, §3 표, §7 표, 첫머리 기준 버전·테스트 개수)를 갱신했다.

전용 중첩 9종: 미식가의 식탁(1), 귀환의 문턱(1), 백색 봉합(1), 정각의 거주(1), 인양의 명패(3), 파단 증언(3), 숙고의 말미(1), 역행하는 별빛(1), 절취선(6). 괄호는 상한.

이 문서의 신규 개념물 5종(10장)이 모두 추가되면 카드 20종 · 전용 중첩 14종(미수금·잔향·좌표 낙인·술래의 눈·용해 추가)이 된다. `test('concept cards are stronger catalogue choices and pay mental cost once on use')`의 `concepts.length`(10→20)와 `conceptStackTraits.length`(9→14) 단언도 함께 갱신해야 한다.

아직 구현되지 않은 신규 카드의 제안 id: `conceptLedgerStart`/`conceptLedgerBill`(외상 장부), `conceptEchoStart`/`conceptEchoChorus`(잔향), `conceptMercuryStart`/`conceptMercuryCollapse`(수은 눈금), `conceptTagStart`/`conceptTagFound`(술래), `conceptDissolveStart`/`conceptDissolveAll`(분해자).
